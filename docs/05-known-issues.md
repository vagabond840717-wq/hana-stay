# 알려진 문제 및 주의사항

이 문서는 코드 작업 시 반드시 확인해야 할 버그, 설계 취약점, 주의사항을 정리한다.

## 🔴 버그 / 데이터 손실 위험

### 1. 호실명 변경 시 비밀번호/메모 데이터 고아(orphan)
**증상**: 호실 이름을 수정하면 해당 호실의 모든 비밀번호·메모가 사라짐  
**원인**: `bkKey = "${roomName}|..."` — 키에 호실명 포함됨  
**해결 방향**: 호실에 고정 UUID 부여 후 키를 `"${roomId}|..."` 로 변경

### 2. 날짜 경계 계산 불일치 (청소 스케줄 vs 예약현황)
**증상**: 두 앱에서 같은 날짜가 다르게 표시될 수 있음  
**원인**: `cellTypeFor` 구현이 두 파일에 독립적으로 존재 → 한 쪽만 수정 시 불일치  
**해결 방향**: 공통 JS 유틸리티 파일 분리 (또는 두 파일 동시 수정)

## 🟡 설계 취약점

### 3. iCal 파서 4개 중복
**위치**: 청소 스케줄 앱 L747~824  
**문제**: `parseIcal`, `parseIcalBooking`, `parseIcalTrip`, `parseIcalLv` 가 거의 동일  
**위험**: 파싱 로직 수정 시 하나만 바꾸면 플랫폼별 동작 차이 발생  
**해결 방향**:
```js
// 현재
parseIcal(text)        // Airbnb: "not available", "airbnb (not available)" 필터
parseIcalBooking(text) // Booking: "closed", "not available", "" 필터
parseIcalTrip(text)    // Trip: "not available", "closed", "" 필터
parseIcalLv(text)      // LV: "not available", "closed", "" 필터

// 개선안
parseIcal(text, skipTitles) // 필터 목록을 인자로 받는 단일 함수
```

### 4. 색상 생성 시 고정 (수정 불가)
**문제**: `color = COLORS[rooms.length % 9]` — 추가 순서로만 결정  
**위험**: 호실 삭제 후 재추가 시 색이 바뀜, 사용자가 직접 지정 불가  
**해결 방향**: 설정 패널에 색상 선택 UI 추가

### 5. KV 저장 실패 감지 불가
**문제**: `fetch(PROXY_URL).catch(()=>{})` — 오류 무시  
**위험**: Worker 장애 시 데이터가 localStorage에만 있고 다른 기기에서 안 보임  
**해결 방향**: 저장 실패 시 UI에 표시 (toast 알림 등)

## 🟢 알고 써야 할 동작 (버그 아님)

### 36. 예약 메모는 퇴실 30일 뒤 자동으로 지워진다 (2026.09.25~)
- 워커가 하루 1회 `퇴실 + 30일` 지난 메모를 비운다. **비밀번호는 남는다.** 되살릴 백업은 없다
- 퇴실일을 모르는 옛 메모는 `입실 + 90일`
- 옛 호실명(`402 JnJ` 등)이나 맞는 예약이 없는 옛 서랍 18개는 목록에 안 올라가 **📝 도 안 뜨고 지워지지도 않는다** (이관 때 판단 보류)
- 반반 칸 상세의 비밀번호 칸은 여전히 하나(맨 앞 예약) — 메모만 손님별로 나뉨

### 8. `cinM`은 0-indexed
모든 Booking 객체의 월 값은 JavaScript Date와 동일하게 0-indexed.  
`cinM = 5` → 6월. 표시할 때만 `cinM + 1`.  
bkKey 생성 시에는 `String(cinM+1).padStart(2,'0')` 로 변환.

### 9. 체크아웃 날은 숙박 중에 포함 안 됨
```js
if (cur > cin && cur < cout) occupied = true;  // strict inequality
```
체크아웃 날(`cur === cout`)은 `occupied` 가 아니라 `checkout` 상태.
**내보내기도 같은 규칙**: `exportIcal`은 `DTEND = cout`을 그대로 쓴다. iCal의 `DTEND;VALUE=DATE`는 포함되지 않는 날이라, 이것만으로 체크아웃 당일(11시 퇴실 → 15시 체크인)이 판매 가능일로 나간다. **여기서 하루를 더 빼면 마지막 숙박일이 열려 오버부킹**(#21).

### 10. 연속 뷰(multi)에서 네비게이션 숨김
```js
document.getElementById('prevBtn').style.visibility = isMulti ? 'hidden' : 'visible';
```
연속 뷰에서는 이전/다음 월 버튼이 숨겨짐. 현재 월(`curM`) 기준으로 6개월 표시.

### 11. syncAll 실패해도 이전 데이터 유지
`rooms[i].bookings`는 `syncAll()` 이전까지는 `[]` 상태.  
`syncAll()` 실패 시 해당 호실 예약이 안 보임 (이전 데이터로 롤백 없음).

### 12. 예약현황 앱의 `manifest.json` 미포함
PWA manifest를 선언하지만 `manifest.json` 파일이 별도로 없음.  
브라우저에서 설치 프롬프트 안 뜰 수 있음.

### 13. Trip.com 예약 경계(tr_cuts)는 로드 시 치환 방식
Trip.com은 연속 예약을 통짜 블락으로 합쳐 보냄 → `tr_cuts`(날짜 하나)로 조각 치환(→ [03-data-model.md](03-data-model.md) 참고).  
- 원본을 **치환**(제거+삽입)하므로 오버부킹 안 남. 조각 경계는 cout-exclusive.
- 경계가 예약 **한가운데**일 때만 자른다. `cin`·`cout`과 같으면 이미 나뉜 상태라 아무것도 안 함.
- 예약이 연장·단축돼도 경계는 살아남는다 (기간 일치 조건이 없음). 그 날짜에 걸친 예약이 피드에서 전부 사라지면 자동 은퇴(`retireCuts`), 피드 로드 실패 시엔 판정 보류.
- 조각마다 체크인이 달라 **비밀번호/메모 키(bkKey)가 조각별로 분리됨** (의도된 동작 — 손님이 다름). 경계를 지우면 통짜 키 하나로 복귀.
- 현재 대상은 **Trip.com만** (`SPLIT_PLATFORMS=['tr']`). 구조는 공통이라 확장 가능.
- 2026.08.06 이전 구조는 `tr_splits`(기간+경계). 기간 완전일치를 요구해 연장 한 번에 무효가 됐다 → #24 참고.

### 18. 경계 확인 알림(⚠)은 예약앱 전용 로직 (2026.07.15 / 2026.08.06 단순화)
직전 피드 스냅샷(`tr_feed_prev`) 비교로 ⚠ 를 띄우는 로직은 **예약앱에만** 있다.  
- 청소앱은 결과 조각만 반영 (KV의 `tr_cuts`를 읽으므로 자동).
- 판정 기준: 경계가 지금 통짜 한가운데에 걸치는데 **직전 피드에는 그 날짜를 덮는 예약이 없었으면** ⚠. 원래도 덮던 예약이 합쳐진 거면 정상 동작이라 조용히 통과.
- 취소+재예약이 새로고침 한 번 사이에 일어나 피드 모양이 동일하면 감지 불가 (경계가 같아 표시는 정확 — 허용된 한계).
- 상세: [features/split-inherit.md](features/split-inherit.md)

### 25. Trip.com은 "문의" 단계에서 이미 날짜를 iCal로 내보낸다 (2026.08.06)
예약 확정 전 **문의/요청만 들어와도** 트립은 해당 날짜를 `RoomStatus Fully booked`로 내보낸다. 거절하면 풀리지만 **즉시가 아니다.**  
- 실측(402호 8/6~8/8 거절): 거절 후에도 30분 이상 남았고, **날짜별로 순차 해제**됐다 (08:57 8/7 해제 → 09:32 8/6 해제).
- 같은 요청에 묶인 날짜가 **일부만 남아 있어도 "다른 이유로 닫힘"이라 단정하지 말 것.** 순차 해제 중일 수 있다.
- 트립 iCal은 **실제 예약과 수동 방닫기를 구분해 주지 않는다** (둘 다 `RoomStatus Fully booked`). 에어비앤비는 `Reserved` / `Airbnb (Not available)`로 구분해 준다 → 트립에서 닫아둔 날은 앱에서 블락이 아니라 체크인 마커로 그려질 수밖에 없다.
- 트립 iCal에는 **가져온 남의 달력이 되비치지 않는다** (우리가 내보낸 에어비앤비·부킹닷컴 블락이 트립 피드에 전혀 없음을 실측 확인). 트립 피드 = 트립 자기 재고 상태만.
- **대응**: "예약앱에서 안 사라진다"는 문의를 받으면 먼저 프록시(`/?url=<trUrl>`)로 트립 원본을 받아 대조한다. 원본에 남아 있으면 앱 문제가 아니다 — 시간을 두고 재확인.

### ~~35. 투숙 중 손님의 입실일이 매일 밀려 보이던 문제 — 복원 재료를 수첩에서 원장으로~~ ✅ 해결 (2026-09-23)

부킹·트립은 투숙 중에도 시작일을 당겨 보낸다(#29). 되돌리는 재료를 **수첩**에서 찾고 있었는데,
찾는 방법이 **"끝날짜가 같은 줄"** 이라 손님이 투숙 중 날짜를 바꾸면 짝이 사라진다.

| 상황 | 수첩으로 복원 | 원장으로 복원 |
|---|---|---|
| 변경 없음 | 맞음 | 맞음 |
| 투숙 중 **연장** (9/23→9/25) | ✗ 입실일 2일 밀림 | 맞음 |
| 투숙 중 **단축** (9/25→9/24) | ✗ 복원 실패 → **오늘 체크인**으로 보임 | 맞음 |

**원장은 '어제 이 방에 있던 손님'으로 찾는다** — 퇴실일이 어떻게 바뀌든 연결이 안 끊긴다.
판정은 `ledgerCin()` 한 곳에 둔다 — `buildDaySegs` 의 입실일 상속과 **같은 규칙**이다 (#2).

**⛔ 어제 원장의 퇴실일이 '오늘'이면 잇지 않는다.**
`같은 손님의 당일 연장` 과 `한 팀 나가고 새 팀 입실` 은 **날짜만으로 구분이 안 된다**
(두 경우의 입력이 완전히 동일함을 실측). 잘못 이으면 **그날 교대 청소가 일정에서 사라진다.**
끊어 보는 쪽이 안전하다 — 최악이라도 안 해도 될 청소를 한 번 더 잡을 뿐이다.

### ~~30. 주차앱만 새벽~오전 9시에 날짜가 하루 밀린다~~ ✅ 해결 (2026.09.09, commit `9d77471`)

**주차앱 혼자 UTC 시계를 읽고 있었다.** 한국은 UTC+9 → **KST 자정~오전 9시 사이엔 언제나 어제 날짜**가 떴다.

```js

//                                     ^^^^^^^^^^^^^ UTC로 변환
// 실측 2026-09-09 08:21 KST → todayStr() === "2026-09-08"
```

**증상이 화면 오류로 끝나지 않는다** — 오늘 입차하는 차가 "빈자리 + 예약1"로 보인다.

**딸린 하루 어긋남 (`autoExpire`)** — 같이 고쳐야 했다.
기준이 `tomorrow` 라서 `end === 오늘`(오늘 출차)인 예약을 지우고 KV에 저장까지 했다.

UTC 오류가 새벽 시간대에만 우연히 이를 막아주고 있었으므로, 날짜만 고치면 새벽에도 지워지기 시작한다.

| | 수정 전 | 수정 후 |
|---|---|---|
| `todayStr()` | `toISOString()` (UTC) | `getFullYear/getMonth/getDate` (기기 로컬) |
| `shiftDate()` | `new Date('YYYY-MM-DD')` = UTC 자정 파싱 | 연·월·일 분해 후 `new Date(y, m-1, d)` |
| `autoExpire()` | `end >= tomorrow` (오늘 출차분 삭제) | `end >= today` (지난 것만 삭제) |

**기기 로컬 시계를 택한 이유 (KST 하드코딩 안 함)** — 예약앱·청소앱이 이미 같은 방식이다.
```js
// booking/index.html:779 · jnjhana/index.html:739 ← 기준 앱, 원래부터 정상
function today() { const d = new Date(); return {y:d.getFullYear(),m:d.getMonth(),d:d.getDate()}; }
```
주차앱만 KST로 못박으면 해외에서 앱을 열 때 **예약앱은 현지 날짜, 주차앱은 한국 날짜**가 되어
두 화면이 서로 다른 날을 가리킨다. 세 앱이 같은 시계를 보는 쪽이 안전하다.

**검증** (배포본에 수정 함수만 갈아끼워 실데이터 대조)

- **조기 퇴실·연장**은 `cout` 이 바뀌어 짝이 안 맞는다 → 안 건드린다
- **판매 오픈 기간 '꼬리' 오판 방지** — ①은 시작이 오늘·어제일 때만 본다.

- ⚠ **서버를 못 읽으면 아예 쓰지 않는다.** 남의 기록을 지우느니 내 저장을 실패시키는 게 낫다. 실패 시 토스트로 알리고 **화면의 낙관적 변경도 되돌린다** (저장 안 된 걸 된 것처럼 두지 않는다)
- `localStorage`는 **서버 저장 성공 후에만** 갱신 → 낡은 로컬본이 폴백으로 되살아나지 않는다
**한계**: 같은 블락을 두 기기가 "동시에" 수정하면 나중에 저장한 쪽이 이김(진짜 동시 편집은 여전히 마지막 쓰기 우선) — 이번 수정은 "낡은 세션이 뒤늦게 무관한 변경을 저장하며 최신 데이터를 지우는" 흔한 경우만 막음.
**후속 과제**: 블락이 삭제되면 그 블락에 달린 메모/비밀번호의 `bkKey`가 `yyyymmdd` 형식(블락 있을 때)에서 `yyyy.mm.dd` 형식(블락 없을 때)으로 바뀌어 조회 불가능한 고아 데이터가 되는 별도 버그 있음 — 미수정.

### ~~21. 내보내기 iCal이 트립·부킹 예약을 하루 짧게 전송 → 마지막 숙박일 오버부킹~~ ✅ 해결됨 (2026.08.05)
**증상**: 트립닷컴 예약 8/17~8/22인데 에어비앤비 달력에 17~20일만 잠기고 **21일(마지막 숙박일)이 판매 가능** 상태. 402·601·603호 등 tr/bk 예약이 있는 모든 호실에서 발생.
**원인**: 워커 `exportIcal`이 tr/bk 예약의 `DTEND`를 하루 앞당겨 내보냄 (2026-08-01 적용, [PLAN-trip-booking-checkout-fix.md](features/PLAN-trip-booking-checkout-fix.md)).
당시 전제 *"Trip.com/Booking.com iCal의 DTEND = 체크아웃 당일(포함)"* 이 **사실이 아니었다.** 실측 확인:

| 트립 예약관리 화면 | 트립 iCal |
|---|---|
| 체크인 8/17, 체크아웃 8/22 | `DTSTART:20260817` / `DTEND:20260822` |

즉 트립도 **표준대로 DTEND exclusive**로 보낸다. 체크아웃 당일은 원래부터 예약 가능일로 나가고 있었는데 거기서 하루를 더 빼서, 체크아웃 당일 + **마지막 숙박일**까지 두 밤이 열렸다.
**수정**: `exportIcal`에서 `if (key==='tr'||key==='bk') coutDate.setDate(-1)` 제거, `DTEND = cout` 그대로 사용. commit 23992de.
**피해 범위**: 우리 피드(`/ical/<호실>`)를 읽는 **모든 플랫폼**(에어비앤비·부킹닷컴·리브애니웨어)에 동일하게 하루 짧게 나갔다. 8/1~8/5 기간 동안 각 예약의 마지막 숙박일이 전 채널에서 판매 가능 상태였음.
**교훈**:
- 플랫폼 iCal의 DTEND 해석을 **추측하지 말고 실제 피드와 예약 화면을 대조**할 것. 프록시로 원본을 그대로 받아볼 수 있다.
- "체크아웃 당일을 팔 수 있게" 하려고 **구간 전체를 당기면 안 된다.** 당일은 열리지만 마지막 숙박일이 같이 열린다. `DTEND = cout` 하나로 이미 충족된다.
- 우리 피드는 에어비앤비 전용이 아니다. 내보내기 변경은 **전 채널 영향**으로 봐야 한다.
- 에어비앤비는 **가져온 달력의 블락을 자기 iCal로 다시 내보내지 않는다.** 그래서 이 증상은 피드로 검증 불가 — 앱 화면을 봐야 확인된다.

### ~~23. ↻ 를 눌러도 취소된 예약이 사라지지 않음 (예약앱)~~ ✅ 해결됨 (2026.08.06)
**증상**: 트립닷컴에서 거절·해제된 402호 8/6 예약이 예약앱 달력에 계속 남음. ↻ 를 몇 번 눌러도 그대로.
새 브라우저로 열면 정상 → 서버 데이터는 이미 깨끗했다.
**원인**: `applyCuts()`가 자르기 전 원본을 `room['_raw_'+key]`에 보관하는데, `mergeArchiveIntoRooms()`가 **첫머리에서 이 백업을 무조건 복원**한다.

```
triggerSync()
  ├ loadBookingsFromKV()      → room.trBookings = 새 피드 (8/6 없음)  ✅
  └ mergeArchiveIntoRooms()
      └ if (r['_raw_tr…']) r.trBookings = r['_raw_tr…']   ← 옛 피드로 되돌림 ❌
      └ … applyCutsAll() → 되돌린 배열을 다시 _raw_ 로 백업 (영구 고착)
```

`_raw_`는 메모리에만 있어 **페이지를 새로 열면 풀리고, ↻ 로는 절대 안 풀린다.** 사용자 화면이 새벽 02:45 시점 피드에 고정돼 있던 이유.
부수 피해로 `detectCutAlerts`(⚠ 배지)도 옛 배열 기준으로 판정했다.
**수정**: `loadBookingsFromKV()`에서 새 피드를 대입한 직후 `delete room['_raw_'+key]`. `mergeArchiveIntoRooms()`의 복원 코드는 **그대로 둔다** — init에서 2회 호출될 때 조각 배열이 백업을 오염시키는 걸 막는 역할(#19)이 여전히 필요하다. commit 7eb5e47.
**교훈**: 캐시·백업을 두는 코드는 **무효화 시점**을 같이 정해야 한다. #19 수정은 "경계 편집 → 재계산" 경로만 보고 "새 피드 수신" 경로를 놓쳤다.

### ~~24. 청소앱이 경계를 전혀 반영하지 못함~~ ✅ 해결됨 (2026.08.06)
**증상**: 예약앱에서 자른 경계가 청소앱에 안 보임. 402호 8/10이 예약앱은 `c-tr-both`, 청소앱은 `c-tr-occupied`.
**손님이 바뀌는 날의 청소가 일정에 안 잡히는** 실질 피해.
**원인**: 예약앱이 분할 저장 구조를 `tr_splits`(기간+경계) → `tr_cuts`(경계 날짜만)로 교체했는데 **청소앱은 여전히 `tr_splits`를 읽고 있었다.** 그 키는 이관 후 비어 있어(`[]`) 모든 경계가 무시됐다.
**수정**: 청소앱 `loadSplits`/`applySplits` → `loadCuts`/`applyCuts`. 읽기 전용 유지(`saveCuts` 없음, 구버전 이관은 예약앱만). commit 39d6f91.
**교훈**:
- **공유 KV 키를 바꾸면 그 키를 읽는 앱을 전부 세어볼 것.** 한쪽만 바꾸면 조용히 어긋난다 — 에러도 안 나고 그냥 기능이 사라진다.
- 두 앱이 같은 데이터를 쓰면 **양쪽 화면을 나란히 대조**해야 발견된다. 코드만 봐서는 안 걸린다.

### ~~27. 사용자가 만든 트립 경계가 저절로 사라짐 (자동 은퇴)~~ ✅ 해결됨 (2026.08.09)
**증상**: 402호 8/10 경계를 잘라뒀는데 어느 날 보면 통짜로 합쳐져 있다. 예약이 돌아와도 경계는 안 돌아와 **매번 다시 잘라야** 했다.
**원인**: `retireCuts()`가 "그 날짜에 걸친 예약이 피드에 하나도 없으면 경계를 거둔다"로 동작했고, 곧바로 `saveCuts()`까지 타서 KV에서 지워졌다.
트립닷컴은 **문의 단계 날짜를 넣었다 뺐다** 하고 거절 후 해제도 30분 이상 날짜별로 순차 진행된다(#25).
그 "예약이 잠깐 사라진" 순간에 앱이 켜지면 사용자가 손으로 만든 경계가 **영구 삭제**됐다.
**수정**: `retireCuts()` 함수·호출·`_cutsRetired` 안내 전부 제거. 경계는 사용자가 해지할 때만 사라진다. commit 46a5d89.
- 부수 효과(의도된 것): `loadBookingsFromKV`가 더는 `trCuts`를 건드리지 않으므로 그 경로의 `saveCuts()`도 사라졌다 → **피드를 못 읽은 상태에서 부분 목록으로 KV를 덮어쓰는 경로**(#22와 같은 모양)가 함께 막혔다.
- 안전망은 `detectCutAlerts`(⚠) 그대로. 남은 경계가 새 통짜 한가운데 걸리면 확인 카드가 뜬다.
- 아무 예약에도 안 걸치는 경계는 `applyCuts`가 지나치므로 화면 무영향.
**검증**: 배포본에서 402호 피드에서 8/8~8/12만 제거 → 옛 코드가 8/10 경계 삭제(재현 성공) / 수정 후 잔존.
현재 실피드로는 `retireCuts()`가 아무것도 지우지 않아(`changed=false`) 화면 영향 0 — 1,935칸 대조 확인. KV `tr_cuts` 값 시험 전후 동일.
**교훈**: **사용자가 손으로 만든 데이터를 자동으로 지우는 규칙은 위험하다.** 외부 피드가 흔들리는 걸 근거로 삼으면
그 흔들림이 사용자 작업을 지운다. 정리가 필요하면 지우지 말고 **물어보거나 그냥 놔둘 것**(안 걸치는 경계는 무해했다).

### ~~26. 경계 목록을 서버에서 못 읽으면 그 화면에서 경계가 전부 사라져 보임~~ ✅ 해결됨 (2026.08.10, commit `80e2e38`)
**증상**: 잘라둔 경계가 통짜로 합쳐져 보임. 새로고침하면 정상.
**원인**: `loadCuts()`는 KV 실패 시 localStorage로 폴백하는데, 그 기기가 경계를 한 번도 저장한 적 없으면 `hana_cuts`가 비어 있다.
그러면 `migrateSplitsToCuts()`로 내려가고 `tr_splits`도 비어 있어 `trCuts = []`가 된다 → 모든 경계가 없는 화면.
**진짜 위험은 화면이 아니라 그다음이었다**: 그 상태에서 경계를 하나 자르면 `saveCuts()`가 **그 하나만 든 배열로 KV를 덮어써** 나머지 경계가 전부 사라진다 (#22와 완전히 같은 모양).
**수정**: #22와 **한 건으로 묶어** 처리 — `saveCuts()` → `saveCutsMerged(op)` (`op = {type:'add'|'remove'}`), 저장 경로는 `saveListMerged` 공용.
- `commitCuts(op)`가 로컬 변경까지 **직접 수행** → 실패 시 이전 상태로 정확히 복원 (호출부가 먼저 바꿔놓으면 되돌릴 기준이 없다)
- 경계 변화 없는 '⚠ 확인만' 경로는 `op=null` → `tr_cuts` write 자체를 생략 (KV 한도 원칙)
- `loadCuts`: **읽기 실패를 '서버가 비었음'으로 오해**해 구버전 이관본으로 서버를 덮어쓰던 경로도 차단. 실패 시 로컬 사본으로 화면만 채우고 저장은 하지 않는다
**검증**: POST를 가로채 payload만 확인(서버 무변경) — 빈 목록에서 추가 시 서버 2건 + 새 1건 저장(옛 코드는 1건만), 삭제 시 대상만 제외, 블락도 동일.
서버 못 읽는 상황 → POST 0회 + 토스트 + 화면 복구. 실서버 왕복(12/25 추가→확인→삭제) 후 원래 2건으로 정확히 복구 확인.
**교훈**: **읽기 실패와 "값이 없음"을 같은 것으로 다루면 안 된다.** 이 버그도, #27(자동 은퇴)도, 뿌리는 같다 —
"못 읽었다"를 "비어 있다"로 해석한 코드가 사용자 데이터를 지웠다.

### 14. `c-bk-both` / `c-lv-both`는 아직 단색 (both 반반셀 미적용)
경계 기능으로 `c-tr-both`는 아웃/인 반반 그라디언트로 수정했으나, Booking.com·리브애니웨어의 both 셀은 여전히 단색.  
해당 플랫폼은 아직 통짜 합침 사례가 없어 both가 드묾. 추후 그 플랫폼 경계를 켤 때 함께 수정 필요.

## 코드 수정 시 체크리스트

기능 추가 또는 수정 전에 반드시 확인:

- [ ] **앱 소스를 깃허브에서 새로 받았는가?** → `E:\airbnb\app/` 는 백업이지 원본이 아니다 (#24 오진 원인)
- [ ] 청소 스케줄 앱과 예약현황 앱이 같은 로직을 쓰는가? → 두 파일 모두 수정
- [ ] **공유 KV 키를 바꾸는가?** → 그 키를 읽는 앱을 전부 세어볼 것. 한쪽만 바꾸면 에러 없이 기능만 사라진다 (#24)
- [ ] **캐시·백업 배열을 두는가?** → 무효화 시점을 같이 정할 것 (#23)
- [ ] iCal 파싱 관련 수정인가? → 4개 parser 모두 확인
- [ ] bkKey 관련 변경인가? → 기존 저장 데이터 마이그레이션 필요
- [ ] `render()` 를 호출하는가? → `attachCellClicks()` 가 같이 실행되는지 확인
- [ ] 날짜 비교 로직인가? → 0-indexed 월 일관성 확인
- [ ] KV 저장/로드인가? → localStorage 폴백 동작도 테스트
- [ ] 배포 전 검증했는가? → 배포본에 수정 함수만 주입 → 전체 셀 클래스 덤프 대조 (부작용 정확히 잡힘)
