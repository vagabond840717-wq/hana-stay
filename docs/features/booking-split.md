>   (각 예약의 체크아웃을 `<input type=date>`로 조정, `＋예약 추가`/`－줄이기` 버튼, 겹치는 날짜 입력 차단).

>   반반 셀(`bothLbl`)에 플랫폼 아이콘(🌐/✈/🏨/🏡) 표시.

## 요약
Trip.com이 연속 예약 여러 건을 하나의 점유 블락으로 합쳐 보내는 문제를, 달력에서 그 블락을 클릭해 실제 체크인/체크아웃 경계로 나누는 기능. 앱이 과거 이력을 근거로 분할을 **추천**하고, 사용자가 **확인**해 확정한다. 분할 결과는 예약앱과 청소앱 양쪽에 자동 반영되며, 오버부킹 오류가 발생하지 않도록 설계한다.

## 목적 및 배경
- Trip.com iCal 피드는 개별 예약이 아니라 **"RoomStatus Fully booked"** 점유 구간(VEVENT 1개)으로 내보낸다. (실측 확인됨)
- 예: 402호 `7/9~7/24` 한 덩어리 = 실제로는 여러 예약.
- 청소 스케줄의 목적은 **체크인/체크아웃 개수 파악**인데, 합쳐진 블락은 중간 경계를 숨겨 청소를 놓치게 한다.
- 파서·렌더 문제가 아니라 **피드 소스가 이미 합쳐 보내는 것** → 앱에서 수동 보정할 수밖에 없다.

### 대상 플랫폼
| 플랫폼 | iCal 발행 방식 | 분할 대상 |
|--------|--------------|----------|
| ✈ Airbnb | 예약 1건 = VEVENT 1개 (확실) | **영구 제외** |
| 🏨 Booking.com | 지금까지 개별 발행, 통짜 사례 없음 | 현재 미대상 (구조만 열어둠) |
| 🏡 리브애니웨어 | 지금까지 개별 발행, 통짜 사례 없음 | 현재 미대상 (구조만 열어둠) |
| 🌐 **Trip.com** | 점유 구간을 한 덩어리로 합침 (확인됨) | **현재 유일 대상** |

→ 지금은 **Trip.com(`tr`)만** 켠다. 내부 로직은 플랫폼 공통으로 만들어, 훗날 다른 플랫폼에서 같은 문제가 생기면 스위치만 켜서 확장한다. (`SPLIT_PLATFORMS = ['tr']` 형태)

## 기능 상세

### 핵심 원칙
1. **원본은 절대 지우지 않는다.** Trip.com 통짜는 피드/KV에 그대로 두고, 그 위에 "이렇게 나눠 보라"는 **분할 메모(포스트잇)**만 얹는다.
2. **앱은 결정하지 않는다.** 이력을 근거로 추천/감지만 하고, 분할·통합의 최종 결정은 항상 사용자가 한다.
3. **원본이 조금이라도 바뀌면 분할은 자동으로 손을 뗀다.** (오버부킹 원천 차단)

### 사용자 시나리오

**A. 분할하기 (이력 기반 추천)**
1. 예약앱 달력에서 합쳐진 Trip.com 블락의 아무 날이나 누른다.
2. 상세 모달에 **분할 추천 카드**가 자동으로 뜬다.
   - 이력에서 이 구간과 맞는 조각: ✓ 자동 채움 (예: `7/9-18`, `7/20-24`)
   - 이력에 없는 조각(중간 빈칸): ⚠️ **"직접 확인 필요"** 표시
3. 그대로 괜찮으면 **[이대로 N건으로 나누기]** 버튼 하나로 확정. 날짜가 틀리면 조각 날짜를 눌러 수정 후 확정.

**B. 분할 후 표시**
- 조각 시작일 → **인** 셀, 끝일 → **아웃** 셀, 앞 조각 끝 = 뒤 조각 시작이 겹치는 날 → **아웃|인 반반** 셀, 사이 날짜 → **점유** 셀.
- 전부 **기존 셀 판별 로직(`cellTypeFor`, `both`/`bothLbl`)이 그대로 그린다.** Airbnb·Booking 예약이 붙어 있을 때와 동일한 모양 → 이질감 없음. 새 CSS·새 로직 불필요.

**C. 되돌리기 / 수정**
- 분할된 블락을 누르면 **[분할 해제]**(포스트잇 제거 → 통짜 복귀), **[분할 수정]**(경계 다시 잡기) 제공. 원본은 그대로라 언제든 가역적.

**D. 손님 취소로 피드가 바뀐 경우 (자동 처리)**
- Trip.com에서 취소되면 피드 통짜가 깨져 다시 쪼개져 온다. (이력에 `7/9-18`, `7/20-24` 개별 기록이 남아있는 것이 그 증거.)
- 저장된 분할 메모는 원본(예: `7/9~24`)과 더 이상 일치하지 않으므로 **자동 무효화** → 바뀐 피드 그대로 표시, 취소된 구간은 빈방.
- 무효화 시 **"예약이 바뀌어 분할이 해제됐어요"** 안내를 띄운다 (조용히 사라지지 않게).

**E. 떨어져 있던 예약이 붙는 경우 (경계 변화 감지)**
- 예: `7/9-18` 손님이 20일까지 연장 → `7/9-20`. 뒤 `7/20-24`와 붙어 통짜 `7/9~24`가 된다.
- 이때 이력의 `7/9-18`로 순진하게 추천하면 **틀린다**(실제 경계는 18이 아니라 20). 이력에 타임스탬프가 없어 앱이 연장인지 새 예약인지 판단 불가.
- 그래서 **자동 판단 금지.** 다음을 감지하면 확인 화면을 띄운다:
  - 예전엔 비어 있던 날이 채워져 통짜가 됐을 때 (붙음)
  - 이력에 경계가 다른 버전이 섞여 있을 때 (`7/9-18` vs `7/9-20`)
  - 이미 분할해둔 원본이 바뀌었을 때
- 확인 화면은 후보(연장형 / 원래대로 / 직접입력 / 통짜유지)를 제시하고 사용자가 고른다. 한 번 정하면 그 결정을 메모에 기억해 다음 동기화 때 다시 묻지 않는다 (원본이 또 바뀌기 전까지).

## 기술 구현 방안 (채택: 로드 시 조각 치환)

### 데이터 (공유 키)
`manual_blocks`와 동일하게 `/extra` KV + `localStorage`에 새 키 **`tr_splits`**(범용화 시 `booking_splits`)로 저장 → 예약앱·청소앱이 같은 키를 읽어 자동 동기화.
```js
// tr_splits: 배열
{
  roomName: "402호",
  platform: "tr",
  origCin:  {y:2026,m:6,d:9},      // 원본 식별 (m=0-indexed)
  origCout: {y:2026,m:6,d:24},
  decided:  true,                   // 경계 변화 감지 시 사용자가 확정했는지
  boundaries: [                     // 경계 날짜들 (원본 cin<경계<원본 cout)
    {y:2026,m:6,d:18},
    {y:2026,m:6,d:20}
  ]
}
```

### 가공 함수 (양쪽 앱 공통 로직)
`applySplits(room)` — 데이터 로드 직후, render 이전에 호출:
- `room.trBookings`를 순회.
- 예약이 어떤 split의 `origCin/origCout`와 **완전히 일치**하면 → 그 1건을 boundaries로 잘라 **N개 조각으로 치환**(원본 제거 + 조각 삽입).
- 일치하는 split이 없으면 그대로 둔다(= 자동 무효). 이때 무효화된 split이 있으면 안내 대상으로 표시.

이 방식의 이점:
- `isOverbooking`, `cellTypeFor`, `openDetail` 등 **기존 함수 무수정** — 이미 가공된 `trBookings`를 그대로 본다.
- 조각들은 `앞.cout === 뒤.cin`(cout-exclusive)이라 경계일에 오버부킹으로 안 잡힌다. (`isOverbooking`은 `cin<cur<cout`만 카운트 — 검증 완료.)

### 추천 로직 (이력 대조)
- 통짜 블락 클릭 시 `/archive`에서 해당 호실·`tr` 이력을 가져와, `origCin~origCout` **범위 안에 들어오는 조각**을 후보로 수집.
- 조각들이 빈틈 없이 연속되면 그대로 추천. 빈칸/겹침/경계 상충이 있으면 시나리오 E의 확인 화면으로 전환.

## 제약 및 주의사항
- **오버부킹 안전 핵심**: 원본은 항상 *치환*, 절대 *추가* 금지. 조각 경계는 cout-exclusive 준수.
- **원본 식별은 완전 일치**(roomName+platform+origCin+origCout). 피드가 바뀌면 매칭 실패 → 자동 무효(원본 표시) + 안내.
- **비밀번호/메모 키(bkKey)는 cin 기반** → 분할 조각마다 cin이 달라 조각별로 새 키가 생긴다. 손님이 다르므로 의도된 동작으로 본다.
- **호실명 변경 시** `tr_splits`의 roomName도 고아됨 (기존 bkKey와 동일 한계).
- 이력에 **타임스탬프가 없어** 시간순 자동 판단 불가 → 경계 변화는 반드시 사용자 확인.
