## 요약
Trip.com 통짜 블락이 바뀌어도(뒤에 새 예약이 붙는 등) 기존에 알고 있던 경계를 새로고침 시 무조건 버리지 않고, **잠정 유지 + "확인 필요" 배지**로 표시하는 기능.

## 목적 및 배경
- 현재 동작: 분할해 둔 통짜의 원본이 조금이라도 바뀌면 분할이 **자동 무효**(토스트 안내 후 삭제) → 달력이 다시 통짜 한 덩어리로 표시됨.
- 사용자 관점: "새 예약이 **뒤에 붙은 것뿐**인데, 새로고침했다고 이미 알고 있던 경계까지 사라져 하나로 합쳐진다."
- 분할 메모가 없던 방도 마찬가지: 어제까지 두 조각으로 따로 오던 예약이 사이가 채워지면 오늘부터 통짜 하나로 옴 → 경계 정보가 화면에서 사라짐.
- 핵심 아이디어: **직전에 보이던 경계는 이미 확정된 사실**(그 날짜에 체크아웃/체크인이 있었음)이므로, 원본이 "확장"된 경우 그 경계를 잠정적으로 이어받을 수 있다. 단, 연장(같은 손님이 더 묵음)일 가능성이 있으므로 **자동 확정은 하지 않고** 반드시 확인 배지를 단다.

### 기존 스펙(booking-split)과의 관계
- booking-split 시나리오 E는 "경계 변화 감지 시 자동 판단 금지, 사용자 확인"을 정했고 이는 유지한다.
- 이번 기능은 그 확인이 이뤄지기 **전까지의 표시 상태**를 바꾸는 것: `통짜로 합쳐 보여줌` → `직전 경계로 잠정 분할해 보여줌 + ⚠ 배지`.
- "원본은 절대 지우지 않는다 / 앱은 결정하지 않는다" 원칙 그대로 유지. 결정 주체는 여전히 사용자.

## 리서치 결과 (요약)
- iCal 자체에는 "이 덩어리가 예약 몇 건인지" 정보가 없음 — 피드는 빈방/점유만 전달. 통짜 문제는 소스 차원 한계라 앱에서 보정하는 게 표준적 접근.
- 캘린더 동기화 업계 표준은 **이전 상태 스냅샷과 비교(diff)** 해서 변경만 처리하는 방식 (Google/Microsoft는 sync token, iCal 폴링 환경에서는 직전 스냅샷 저장 후 비교).
- "연장 vs 새 예약 붙음"을 피드만으로 구분하는 방법은 존재하지 않음(리서치로도 확인) → 잠정 표시 + 사용자 확인이 유일하게 안전한 UX.

## 기능 상세

### 사용자 시나리오
**A. 분할해 둔 통짜가 뒤로 길어짐** (예: `7/9~18|20~24`로 분할해 둔 `7/9~24`가 `7/9~28`로)
1. 새로고침 → 앱이 "같은 시작일, 끝만 늘어난" 원본을 감지.
2. 기존 경계(18, 20)에 **옛 끝날(24)을 새 경계로 추가**해 잠정 분할 생성. (뒤에 붙었다면 24가 새 손님의 체크인일)
3. 달력엔 기존처럼 조각으로 표시 + 해당 블락에 **⚠ 확인 필요 배지**.
4. 블락을 누르면 확인 카드: **[이대로 확정]** / **[마지막 손님이 연장한 거예요]**(옛 끝 경계 제거) / **[직접 수정]** / **[통짜로 유지]**.
5. 확정하면 배지 제거, 다음 동기화부터 일반 분할과 동일.

**B. 분할 메모가 없던 두 조각이 하나로 붙음** (예: `7/9~18` + `7/20~24`가 사이가 채워져 `7/9~24` 통짜로)
1. 앱이 직전 피드 스냅샷과 비교해 "예전 조각들의 합집합 + α = 새 통짜"임을 감지.
2. 예전 조각 경계(18, 20)로 잠정 분할 생성 + ⚠ 배지. (사이에 새로 채워진 `18~20`은 "직접 확인 필요" 조각)
3. 이후 흐름은 A와 동일.

**C. 통짜가 줄어들거나 쪼개짐 (취소)** — 현행 유지
- 피드가 알아서 쪼개져 오므로 잠정 유지 불필요. 기존대로 자동 무효 + 안내.
- 스냅샷은 항상 "가장 최근 피드 모양"으로 갱신 → 쪼개진 상태가 새 기준이 됨.

**C-2. 취소로 쪼개졌다가 그 자리가 다시 채워짐** (사용자 확인 완료 시나리오)
- 예: `9~18|18~20|20~24` 중 가운데 취소 → 피드가 `9~18` + `20~24`로 쪼개져 옴 (C 처리) → 새 손님이 `18~20` 예약 → 다시 `9~24` 통짜로 옴.
- 직전 스냅샷(두 덩어리)과 비교해 시나리오 B로 처리: 경계 18·20으로 잠정 분할, **새로 채워진 가운데 조각에 ⚠ 확인 필요**.
- 한계(허용): 취소+재예약이 새로고침 한 번 사이에 일어나 피드 모양이 어제와 동일하면 감지 불가 — 단 경계가 같아 달력 표시는 여전히 정확하고, 손님 교체 여부는 사용자가 예약 확정 과정에서 인지.

**D. 판단 애매 (시작일도 바뀜, 스냅샷 없음 등)** — 현행 유지
- 자동 추론하지 않고 통짜 그대로 표시. (기존 수동 분할 흐름 사용 가능)

### UI/UX
- 잠정 분할 조각 셀: 기존 조각 렌더 그대로 + **달력 셀 위에 작은 ⚠ 배지** (확정: 사용자가 옵션 1 선택 — 열자마자 보이게).
- 잠정 생성 시 토스트: `"402호 예약이 바뀌어 경계를 잠정 유지했어요 — 눌러서 확인해 주세요"` (기존 해제 토스트를 대체). 토스트는 보조 수단일 뿐, 상태 전달의 본체는 배지.
- 상세 모달 상단에 확인 카드(위 A-4 선택지). 확인 전까지 배지 유지, 동기화마다 다시 묻지 않음.

### 확인 전까지 절대 조용히 넘어가지 않기 (사용자 요구 핵심)
> 배경: 현재 무효화 안내는 2초 토스트 1회 → 놓치면 통짜로만 보이고 변화를 인지할 방법이 없음.
1. **배지는 저장되는 상태**: ⚠는 `decided:false` split(또는 미해결 변경 기록)에서 파생 — 새로고침·기기 변경과 무관하게 사용자가 확인 카드에서 선택하기 전까지 유지.
2. **로드 실패 시 판정 보류**: 스냅샷·분할 데이터를 못 불러온 경우(통신 실패 등) 무효화·스냅샷 갱신·잠정 생성 모두 보류. 기억을 지우거나 덮어쓰지 않고 다음 성공 시 처리. (기존 applySplits의 "원본 비었으면 판정 보류"와 동일 원칙)
3. **승계 불가 변화도 배지**: 자동으로 경계를 못 잡는 변화(시나리오 D 포함)는 통짜로 표시하되 그 블락에 ⚠ 배지 + "예약이 바뀌었어요" 확인 카드. 어떤 경로로도 "말없이 통짜 표시"는 없음 — 기존 `notifyStaleSplits`의 "삭제+토스트" 동작을 "보류+배지"로 대체.

### 동작 규칙
- 잠정 분할은 `decided:false` 상태의 split — 저장/동기화는 기존 `tr_splits`와 동일 경로.
- 승계 조건(엄격): 같은 호실·플랫폼에서 ① 새 통짜가 옛 통짜(또는 옛 조각들의 범위)를 **완전히 포함**하고 ② 기존 경계들이 모두 새 통짜 내부에 있을 때만. 하나라도 어긋나면 승계 포기(현행 무효 처리).
- 앞이 길어진 경우도 대칭 처리(옛 시작일이 새 경계 후보).
- 오버부킹 안전: 기존 `applySplits`의 치환(제거+삽입) 방식 그대로 사용 — 새 로직이 셀 판별·오버부킹 감지 함수를 건드리지 않음.

## 기술 구현 방안

### 옵션 A — 기존 분할 정의만 승계 (최소 구현)
- `notifyStaleSplits()` 전에 승계 검사: 무효 판정된 split의 원본과 "같은 cin, 더 늦은 cout"(또는 대칭) 통짜가 있으면 split의 orig를 갱신하고 옛 끝날을 경계로 추가, `decided:false`로 저장.
- 장점: 변경 범위 최소(예약앱 1개 함수 + 확인 UI). 스냅샷 저장 불필요.
- 한계: **시나리오 B(분할 메모 없던 조각 합쳐짐)를 못 잡음** — 사용자가 실제 겪은 상황이 B일 가능성이 높음.

### 옵션 B — 직전 피드 스냅샷 diff (권장)
- 매 로드 시 호실별 Trip.com 통짜 목록(원본 raw)을 `tr_feed_prev`로 저장 (localStorage + KV `/extra`).
- 다음 로드에서 현재 피드와 비교: 새 통짜가 직전 조각 여러 개(또는 확장된 옛 통짜)를 포함하면 직전 경계로 잠정 분할 자동 생성.
- 기존 split 승계(옵션 A 로직)도 이 비교 안에 자연히 포함됨.
- KV 쓰기는 **스냅샷이 실제로 바뀐 경우에만** 실행 (KV write 한도 원칙 준수).
- 장점: 사용자가 겪은 A·B 모두 해결. 아카이브에 의존하지 않음.
- 단점: 새 저장 키 1개 추가, 로드 경로에 비교 단계 추가.

### 옵션 C — 아카이브 이력 기반 자동 잠정 분할
- 기존 `recommendSplit()`(아카이브 대조)을 클릭 시가 아니라 로드 시 자동 실행해 잠정 분할 생성.
- **채택 곤란**: 2026.07.08의 스냅샷 중첩 제거 수정(#17)이 "다른 항목에 완전히 포함되는 항목"을 아카이브에서 지우므로, 통짜가 커지는 순간 **경계의 증거가 되는 옛 조각들이 먼저 삭제**됨. 이 기능의 근거 데이터로 신뢰 불가.

**권장: 옵션 B.** (A는 B의 부분집합. C는 #17과 충돌.)

- `tr_splits` 항목: 기존 `decided:false`를 "잠정(확인 필요)" 의미로 사용 — **구조 변경 없음**, 마이그레이션 불필요.

## 제약 및 주의사항
- **연장 오인 위험**: 마지막 손님이 연장한 경우 잠정 경계(옛 끝날)는 틀린 정보 — 그래서 반드시 ⚠ 배지 + 확인 카드. 배지가 있는 동안은 "잠정"임을 UI가 명확히 해야 함.
- **KV write 한도**: 스냅샷은 변경 시에만 write (매 로드 무조건 write 금지 원칙 — `project-kv-write-limit`).
- **known-issues 관련**: #13(tr_splits 치환 방식) 동작 설명 갱신 필요, #17(아카이브 중첩 제거)이 옵션 C를 막는다는 상호작용 기록.
- 청소앱/예약앱 로직 분리(#2)와 동일한 한계: 승계 로직은 예약앱에만 존재 — 문서에 명시.
- 호실명 변경 시 스냅샷도 고아됨 (기존 bkKey·tr_splits와 동일 한계).
