# 트립 당일잠금 걷어내기 (trip-daylock) 스펙

## 요약
트립의 자동 규칙 `전략 제어 – 당일 객실 마감`이 매일 **KST 18:00에 만드는 "오늘 하룻밤" 가짜 블락**을,
**낮에 봐둔 기록**과 대조해 걷어낸다. 화면·장부·내보내기 세 곳에 적용하되 내보내기는 마지막에 켠다.

---

## 목적 및 배경

### 발단 (2026-09-02 01:11, 402호)
트립 예약 목록에는 `CHANG/YUNING 9/2 → 9/11` 인데 예약앱은 **9/1 체크인**으로 표시했다.

| 확인 대상 | 값 |
|---|---|
| 트립 원본 iCal (`DTSTAMP 20260901T161509Z` = KST 09-02 01:15) | `DTSTART:20260901` / `DTEND:20260911` |
| 트립 예약 관리 화면 | `2026-09-02 → 2026-09-11` (1객실, 처리된 예약) |
| KV `synced_bookings` 402 jnj `tr` | `2026-09-01 → 2026-09-11` |

**앱은 피드를 정확히 그렸다.** 트립이 틀린 것을 보냈다.

### 원인 — [#28](../05-known-issues.md)의 규칙, 반대쪽 끝
`전략 제어 – 당일 객실 마감`이 매일 `17:59:59`에 그날을 만실로 바꾸고 다음날 `07:00`에 되돌린다.
트립 iCal은 손님 밤과 잠긴 밤을 똑같이 `RoomStatus Fully booked`로 내보내고,
**날짜가 맞닿으면 한 덩어리 VEVENT로 합쳐** 보낸다.

```
9/1  밤   트립이 스스로 잠금 (손님 없음)   ┐
9/2  밤   ┐                              ├ 한 줄로 뭉쳐 20260901~20260911 (10박)
  ⋮       ├ 진짜 손님 CHANG/YUNING (9박)  ┘
9/10 밤   ┘
```

가짜 1박 + 진짜 9박 = 10박. 파일의 `9/1~9/11`과 정확히 일치한다.

**#28에는 퇴실 쪽만 적혀 있었다.** 같은 규칙이 예약 시작일 바로 앞 밤을 잠그면 **입실이 하루 당겨진다.**
네 가지 모양이 전부 같은 원인이다:

| 모양 | 조건 | 결과 |
|---|---|---|
| A 홀로 | 앞뒤 다 빔 | 가짜 1박 블락이 통째로 생김 |
| B 입실 쪽 | 내일 입실 예약 있음 | **입실이 하루 당겨짐** ← 이번 건 |
| C 퇴실 쪽 | 오늘 퇴실 예약 있음 | 퇴실이 하루 밀림 ← #28 원본 |
| D 양쪽 | 오늘 퇴실 + 내일 입실 | 두 손님이 한 덩어리로 붙어 **경계가 사라짐** |

### 실측 증거 (알림 로그 `/push/events`, KST)

```
08-25 18:00:57  402 jnj  2026/08/25 ~ 2026/08/26   ← 재점화. 이후 매일 18시 정각
08-26 18:00:57  402 jnj  2026/08/26 ~ 2026/08/30
08-27 07:00:55  402 jnj  2026/08/27 ~ 2026/08/30   ← 07시 해제. 트립이 스스로 고쳐 보냄
08-30 18:00:59  402 jnj  2026/08/29 ~ 2026/08/31
08-31 18:01:01  402 jnj  2026/08/31 ~ 2026/09/01
09-01 18:00:58  402 jnj  2026/09/01 ~ 2026/09/11   ← 이번 건
```

- **매일 `18:00:5x`.** 5분 크론이 `17:59:59` 변경을 첫 차례에 잡은 것
- **`07:00:55` 해제도 잡혔다** → #28의 시간표(18시 잠금 / 07시 해제)를 독립 재확인
- **601·603은 20일치 로그에 18시대 이벤트 0건** → 이 규칙은 402호에만 걸려 있다 (#28도 같은 결론)

### 언제부터인가 — 8/25 재점화

| 기간 | 18시 자동 잠금 | 근거 |
|---|---|---|
| 6월 ~ 8월 초 | **없음** | 402호 빈 날 16일 동안 하룻밤 조각 0개 (아카이브) |
| 8/10 ~ 8/12 | 있음 | #28. 8/12 18:50 사용자가 수동 해제 |
| 8/13 ~ 8/24 | **없음** | 12일간 18시 이벤트 0건 (빈 날 5일 있었는데도) |
| **8/25 ~ 현재** | **매일** | 위 로그 |

**8/25에 다시 켜졌다.** 그 전 12일은 조용했다.

### ⭐ 2차 피해 — 장부가 가짜를 영구 채택한다 (더 중요)

`syncAllRooms`의 아카이브 병합에는 **"포함되는 짧은 쪽을 버린다"** 규칙이 있다
([worker.js:357-369](../../ical-proxy/worker.js)). 트립 앞잘림(같은 숙박을 매일 앞을 잘라 다시 보냄) 대비용 **정답**이다.

**그런데 가짜 블락은 예약을 항상 길게 만든다 → 이 규칙이 매번 가짜를 고른다.**

```
8/26 18:00  트립: 8/26~8/30  (가짜 + 진짜)   → 장부에 들어감
8/27 07:00  트립: 8/27~8/30  (진짜)          → "짧으니 잘린 버전"으로 판단해 버려짐
                                              장부에 남은 것 = 가짜
```

**트립은 제대로 고쳐 보냈는데 우리 장부가 거절했다.** 현재 오염 5건:

| 장부에 남은 가짜 | 잠긴 밤 | 교정값 |
|---|---|---|
| `08-25 ~ 08-26` | 8/25 | (통째로 삭제 — 순수 가짜) |
| `08-26 ~ 08-30` | 8/26 | `08-27 ~ 08-30` |
| `08-29 ~ 08-31` | 8/30 | `08-29 ~ 08-30` |
| `08-31 ~ 09-01` | 8/31 | (통째로 삭제 — 순수 가짜) |
| `09-01 ~ 09-11` | 9/1 | `09-02 ~ 09-11` |

**교정 규칙이 실측으로 검증된다** — `08-26~08-30`의 교정값 `08-27~08-30`이
트립이 다음날 07:00에 실제로 보낸 값과 **바이트 단위로 일치**한다.

**화면은 아침 7시에 저절로 낫지만 장부는 안 낫는다. 매일 하나씩 늘어난다.**
그리고 `mergeArchiveIntoRooms`가 `cout < 오늘`인 것을 복원하므로,
**9/11이 지나면 그 구간이 장부 기준으로 바뀌면서 9/1 체크인이 영구 고착된다.**
청소 횟수 통계(`calcCleanings`)도 장부를 세므로 함께 틀어진다.

### 3차 피해 — 가짜가 다른 채널로 나간다

`exportIcal`은 `synced_bookings`를 그대로 읽는다 ([worker.js:737](../../ical-proxy/worker.js)).
따라서 가짜 블락이 `/ical/<호실>/{ab,bk,lv}` 로 나가 **에어비앤비·부킹닷컴·리브애니웨어에서도 그 밤이 막힌다.**

**사장님 의도는 트립만 닫는 것이다.** 나머지 세 채널은 그 밤을 팔 수 있어야 한다.
손해 크기: 매일 **KST 18:00 ~ 24:00**, 3개 채널. (07:00 해제 시점엔 그 밤이 이미 지났다)

## 기능 상세

### 사용자 시나리오
사장님은 아무것도 새로 하지 않는다. 트립 설정도 그대로 둔다.
차이는 **저녁에 봐도 날짜가 맞고, 다른 채널에서 오늘 밤이 팔린다**는 것뿐이다.

### UI/UX
**화면 변화 없음.** 새 버튼·새 화면·새 표식 없다. 저녁 시간대 날짜가 정확해질 뿐이다.

### 판별 규칙 — 자물쇠 두 개

> **낮에 비어 있던 밤이, 18시 동기화에서 갑자기 막혔으면 = 트립이 건 가짜**

| | 확인할 것 | 왜 |
|---|---|---|
| **자물쇠 1** | 안전창(KST 07:30~17:30) 마지막 관측에 **그 밤이 비어 있었다** | 손님이 있었으면 낮에도 막혀 있었을 것 |
| **자물쇠 2** | 그 블락이 **KST 18:00~18:10 동기화**에서 처음 나타났다 | 자동 규칙의 지문. 사람이 손으로 막으면 시각이 어긋난다 |

**둘 다 맞을 때만 걷어낸다.** 하나라도 어긋나면 지금과 똑같이 동작한다(원본 그대로).
**헷갈리면 무조건 막는 쪽**이다 — 오버부킹이 나는 방향으로는 절대 틀리지 않는다.

**예약 마감 12:00 설정이 이 판정을 안전하게 만든다** (2026-09-02 사장님 변경).
트립이 낮 12시 이후 당일 예약을 안 받으므로, **17:30 이후 트립에 진짜 손님이 새로 생길 수 없다.**
따라서 저녁에 새로 막힌 밤은 트립 자동 규칙 말고는 원인이 없다.

### 걷어내기 = 구간 뺄셈

잠긴 밤 `[오늘, 오늘+1)` 을 트립 조각에서 뺀다.

```
[9/1, 9/11) − [9/1, 9/2)   =  [9/2, 9/11)              ← B 입실 쪽
[8/10,8/13) − [8/12,8/13)  =  [8/10,8/12)              ← C 퇴실 쪽
[8/10,8/15) − [8/12,8/13)  =  [8/10,8/12) + [8/13,8/15) ← D 양쪽 (경계 복원)
[9/1, 9/2)  − [9/1, 9/2)   =  (없어짐)                  ← A 홀로
```

### 안 하는 것 (되열지 말 것)

| | 왜 |
|---|---|
| 트립 `전략 제어` 끄기 | **오버부킹 방어다.** iCal 반영 시차 동안 다른 채널 예약이 트립에 안 닿는다. 유지 |
| 예약 마감 12:00 되돌리기 | 청소 시간 확보 + 위 판정 안전성. 유지 |
| 장부 "긴 쪽 남기기" 규칙 제거 | **앞잘림 방어에 필수.** 빼면 같은 숙박이 매일 다른 예약으로 쌓여 오버부킹 오판까지 난다 |
| `/?url=` 프록시 응답 교정 | #28 판별 순서 1번이 "원본을 받아 대조"다. 진단 경로를 오염시키면 안 된다 |
| 수동 블락 경로 | `extra_manual_blocks`는 별도 서랍·별도 VEVENT. 뺄셈이 닿지 않는다 (아래) |

## 기술 구현 방안

### 원본은 그대로, 읽는 쪽에서 갈린다

```
트립 원본 (synced_bookings)          ← 손대지 않는다
   ├─ 장부 저장 (booking_archive)  → 뺄셈 적용   [A]
   ├─ GET /bookings                → 뺄셈 적용   [C] 예약앱
   ├─ GET /ical/<호실>/<채널>       → 뺄셈 적용   [D] 마지막에 켬
   └─ GET /?url=                   → 원본 그대로  진단용. 불변
```

`synced_bookings`를 안 건드리므로 **되돌리기가 스위치 하나**다.

### 새 KV: `tr_daylock` (워커만 쓴다 — 앱은 안 읽는다)

```js
{
  day:  "20260902",                    // KST 기준 오늘. 날짜 바뀌면 통째로 새로 만든다
  seen: { "402 jnj": false,            // 안전창 마지막 관측: 오늘 밤이 피드에 덮여 있었나
          "601 jnj": false,
          "603 jnj": true },
  fake: { "402 jnj": { min: 1080 } }   // 가짜 판정된 방 + 처음 감지된 KST 분 (18:00 = 1080)
}
```

- **안전창(07:30~17:30)**: `day`가 오늘이 아니면 새로 만든다. `seen[방]` 갱신. `fake` 비움
- **안전창 밖**: `seen[방] === false` 인데 지금 피드가 오늘 밤을 덮으면 → `fake[방] = { min }` 기록
- `fake[방]` 이 있는 동안 그 방의 `tr` 조각에서 오늘 밤을 뺀다
- 내용이 안 바뀌면 **KV write 생략** (한도 원칙, [project-kv-write-limit])

**#22·#26 위험 없음** — 워커만 쓰고 앱은 안 읽으므로 기기 간 덮어쓰기가 성립하지 않는다.

### 적용 조건

| 대상 | 필요한 자물쇠 | 이유 |
|---|---|---|
| 장부 [A] | 1 + 2 | 영구 기록이라 되돌리기 비쌈 |
| 화면 [C] | 1 + 2 | 두 앱 표시 일치 유지 |
| 내보내기 [D] | 1 + 2 | 오버부킹 위험 (#21) |

세 곳 모두 같은 판정을 쓴다 → **판정 함수는 하나만 존재한다** (#2 복제 위험 회피).

### 실패 시 동작

| 상황 | 동작 |
|---|---|
| 안전창에 피드를 못 받음 (연결 오류) | `seen` 갱신 안 됨 → `day`가 오늘이 아니면 **교정 안 함** |
| 18:00 차례를 놓침 (18:10 이후 첫 감지) | 자물쇠 2 실패 → **교정 안 함** |
| `tr_daylock` 읽기 실패 | **교정 안 함** |

**전부 "지금과 똑같이 동작"으로 떨어진다.** 헛짚어서 진짜 예약을 지우는 경로가 없다.

### 수동 블락은 구조적으로 안전하다

`exportIcal`은 플랫폼 예약 루프가 끝난 뒤 `extra_manual_blocks`를 **별도로 순회해 별도 VEVENT**를 만든다
([worker.js:783-794](../../ical-proxy/worker.js)). 트립 조각을 어떻게 주무르든 손이 닿지 않는다.

⇒ **사장님 블락이 항상 최종 결정권.** 얼리체크인·레이트체크아웃은 블락으로 막으면 그대로 나간다.
(2026-08-09 `7035538`에서 **체크아웃만 있는 날에도 블락 버튼이 뜨도록** 이미 만들어 뒀다)

### 소급 청소 (1회성)

`/push/events`의 `18:00~18:10` 도장이 찍힌 트립 이벤트로 가짜를 특정해 장부를 교정한다.
위 표의 5건. **삭제가 아니라 교정**이다 — 그냥 지우면 진짜 숙박이 통째로 사라진다.

한계: 알림 로그는 50건 상한이라 **8/12까지만 남아 있다.** 8/25 재점화 이후 전부 포함되므로 실용상 충분하다.
