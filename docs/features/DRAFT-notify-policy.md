# 알림 정책 개편 (notify-policy) 스펙

## 요약
매일 반복되는 "📅 새 예약" 오탐 알림을 폐지하고, **진짜 조치가 필요한 일**(오버부킹 · 예약 취소 · iCal 연결 오류/복구)만 알리도록 알림 종류를 재정의한다.

## 목적 및 배경

### 지금 무슨 일이 벌어지고 있나

2026-08-14 ~ 08-19 알림 내역 (601 jnj, Trip.com):

| 시각 | 내용 |
|------|------|
| 8/14 | Trip.com 2026/08/14~2026/08/23 새 예약 |
| 8/16 01:00 | Trip.com 2026/08/15~2026/08/23 새 예약 |
| 8/18 01:35 | Trip.com 2026/08/17~2026/08/23 새 예약 |
| 8/19 01:01 | Trip.com 2026/08/18~2026/08/23 새 예약 |

**전부 같은 한 건의 숙박이다.** 끝날짜(08/23)는 그대로인데 시작일만 하루씩 밀린다.

### 원인 — 트립의 "앞잘림" × 워커의 예약 식별 방식

트립 iCal은 **진행 중인 숙박에서 이미 지나간 날짜를 앞에서 잘라내고** 보낸다
([project-trip-past-trimming] 메모, [worker.js:333](../../ical-proxy/worker.js) 주석).
그런데 워커는 예약을 이렇게 구분한다:

```js
// worker.js:294
const uid = `${b.cinY}_${b.cinM}_${b.cinD}_${b.coutY}_${b.coutM}_${b.coutD}`;
```

**체크인 날짜가 이름표에 들어 있다.** 그래서 트립이 앞을 자르는 순간 이름표가 바뀌고,
워커는 "처음 보는 예약"으로 판단해 매일 새벽 푸시를 보낸다.
(트립 UID를 쓸 수 없어 날짜로 이름표를 만든 것 자체는 불가피했다 — 트립은 UID가 매 요청 바뀐다.)

투숙 기간이 열흘이면 **알림이 열 번 온다.** 601호가 지금 그 상태다.

### 왜 "고치기"가 아니라 "없애기"인가

앞잘림 오탐만 막아도 증상은 사라진다. 하지만 사용자 판단은 **새 예약 알림 자체가 쓸모없다**는 것이다:

- 새 예약은 이미 각 채널(에어비앤비·부킹·트립) 앱에서 직접 알림이 온다 → **중복**
- 새 예약은 **손 쓸 일이 없다.** 알림을 보고 할 행동이 없다
- 반대로 **오버부킹·취소·연결 끊김은 즉시 손을 써야 하는데** 지금 푸시가 없거나 묻힌다

업계 표준도 같다 — "알림을 받고 취할 구체적 행동이 없다면 그 알림은 존재하지 말아야 한다"
(actionable-only), "원인이 아니라 증상에 알림을 건다"(symptom-based).
지금 구조는 정확히 그 반대다. **원인(피드에 새 줄이 생김)에 알림을 걸어 놓고,
정작 증상(같은 날 두 팀이 잡힘)은 화면을 열어봐야만 안다.**

## 기능 상세

### 알림 종류 재정의

| 타입 | 지금 | 개편 후 | 이유 |
|------|------|---------|------|
| `new` 새 예약 | 📅 발송 | **폐지** | 조치할 게 없음 + 채널 앱과 중복 + 앞잘림 오탐의 근원 |
| `cancel` 예약 취소 | 계산만 하고 미사용 (worker.js:307) | **신설** 📌 | 방이 비었다 → 되팔아야 함. 조치 필요 |
| `overbook` 오버부킹 | 화면 빨간 셀만, 푸시 없음 | **신설** 🚨 | 손님 두 팀이 같은 날 → 즉시 조치. 가장 급한 일 |
| `error` 연결 오류 | ⚠️ 발송 | **유지** | 피드가 끊기면 오버부킹으로 이어짐 |
| `recovered` 복구 | ✅ 발송 | **유지** | 오류 알림 auto-resolve 쌍 |
| `test` 테스트 | 🔔 발송 | **유지** | 푸시 설정 확인용 |

### UI/UX

알림 카드는 기존 형식 그대로, 타입만 추가한다.

| 타입 | 아이콘 | 제목색 | 미확인 배경 | 본문 |
|------|--------|--------|-------------|------|
| `overbook` | 🚨 | `#991b1b` | `#fef2f2` | `2026/09/12 — Airbnb · Trip.com 겹침` |
| `cancel` | 📌 | `#b45309` | `#fff7ed` | `Booking.com 2026/09/05~2026/09/08 취소` |

- `overbook`은 겹침 해소 시 `error`→`recovered`와 같은 방식으로 **자동 확인 처리**한다.
  단, 복구 알림(✅)은 따로 보내지 않는다 — 겹침이 풀렸다는 건 사용자가 직접 조치한 결과라 이미 안다.

## 동작 규칙 (핵심)

### 1. 취소 판정 — uid 비교가 아니라 **날짜 커버리지** 비교

`cancelled = prevUids - uids` 를 그대로 알림으로 만들면 **새 예약 알림과 똑같은 오탐이 난다.**
트립은 앞잘림·뭉침·분할로 uid가 매일 바뀌기 때문이다. 그래서 이렇게 판정한다:

```
사라진 예약 X 에 대해:
  1. X가 덮던 숙박일 중 오늘 이후 날짜만 남긴다  → future(X)
  2. future(X)가 비었다                          → 시간이 지나간 것. 알림 없음
  3. future(X)의 날짜가 같은 호실·같은 채널의 현재 예약들로 여전히 전부 덮여 있다
                                                 → 뭉침/분할/앞잘림 변형. 알림 없음
  4. 어느 하루라도 덮이지 않고 비었다              → 진짜 취소. 그 빈 구간만 알림
```

이 규칙은 [project-trip-past-trimming] 메모의 판별 규칙과 동일하며,
**트립이 뭉치든 나누든 앞을 자르든 전부 통과한다.** 실제로 "방이 비었다"일 때만 울린다.

> ⚠ 판정은 **채널별로 따로** 한다. 트립 예약이 사라진 자리를 에어비앤비 예약이 덮고 있어도
> 그건 취소가 맞다(다른 채널로 팔린 게 아니라 트립 건이 없어진 것). 채널을 섞으면 진짜 취소를 놓친다.

### 2. 오버부킹 판정 — 앱의 `isOverbooking()` 규칙을 워커로 이식

앱 [index.html:1203](https://github.com/vagabond840717-wq/booking) 규칙 그대로:

```js
// 그 날짜에 "숙박 중"인 예약이 2건 이상이면 오버부킹
cur > cin && cur < cout   // 체크인 당일 = 숙박 O, 체크아웃 당일 = 숙박 X
```

- **오늘 이후 날짜만** 판정 (앱과 동일. 지난 날짜는 아카이브에 취소건이 남아 겹쳐 보임)
- 4채널 전부 합쳐서 계산 (`ab + bk + tr + lv`)
- `not available` / `closed` 블락은 제외 (기존 파서 필터 그대로)
- **트립 `tr_cuts` 조각은 워커가 모른다** → 워커는 통짜로 계산한다.
  같은 채널 내부에서 경계로 나뉜 조각들은 서로 인접할 뿐 겹치지 않으므로 **판정 결과는 같다.**
- 중복 방지: `(호실, 날짜)` 조합에 **미확인 `overbook` 이벤트가 이미 있으면 발송하지 않는다**
- 자동 해소: 미확인 `overbook` 이벤트의 날짜가 더 이상 겹치지 않으면 `read:true` 처리

### 3. KV 쓰기 한도

- 겹침이 없는 평소에는 **KV 읽기·쓰기 0회 추가** (기존 events 로드는 복구 감지용으로 이미 하고 있음)
- events 저장은 지금처럼 루프 종료 후 **1회 일괄 쓰기**로 모은다
  ([project-kv-write-limit] 원칙 — 매 cron 무조건 write 금지)

## 기술 구현 방안

### 옵션 A — 새 예약 알림만 끄기 (최소 변경)
`saveEvent({type:'new'})` + `sendPushToAll` 두 줄 제거. 끝.
- 장점: 30분. 위험 거의 0
- 단점: **사용자가 원한 취소·오버부킹 알림이 안 생긴다.** 알림함이 연결 오류 때만 울리는 반쪽

### 옵션 B — 새 예약 폐지 + 취소·오버부킹 신설 (권장) ⭐
위 동작 규칙 전부 구현.
- 장점: 요청한 정책 그대로. **알림 수는 줄고 가치는 올라간다**
- 단점: 취소 판정 로직이 새로 들어감(약 40줄). 검증 필요
- 위험 관리: 워커의 `syncAllRooms` **읽기 경로만** 손댄다. `synced_bookings`·`archive`·`/ical` 내보내기는
  **한 줄도 건드리지 않는다** → 달력 표시·오버부킹 셀·경계(`tr_cuts`)·내보내기에 영향 없음

### 옵션 C — 알림 기능 전체 제거
🔔 버튼·푸시 구독·events KV 전부 삭제.
- 단점: 되돌리기 비쌈. 사용자가 남기고 싶다고 한 오버부킹·취소·연결오류까지 사라짐. **반대**

**→ 옵션 B 권장.**

## 데이터 변경

- Push Event 객체에 타입 2종 추가: `overbook`, `cancel`. **구조는 기존과 동일**
  ```js
  { id, type:'overbook', room, platform:'Airbnb · Trip.com', cin:'2026/09/12', cout:'', ts, read }
  { id, type:'cancel',   room, platform:'Booking.com', cin:'2026/09/05', cout:'2026/09/08', ts, read }
  ```
- `prev_uids` KV: **구조 변경 없음.** 이미 `{uid: 예약객체}` 맵으로 저장돼 있어 날짜 비교에 필요한 값이 다 있다
- 기존 데이터 마이그레이션 **불필요**. bkKey·Room 객체·`tr_cuts`·`manual_blocks` 전부 무관

## 제약 및 주의사항

- **[05-known-issues.md] #21 (오버부킹 / DTEND)** — `/ical` 내보내기 경로는 이번 작업에서 **전혀 건드리지 않는다**

  `saveListMerged` 대상이 아니다. 다만 **"못 읽었다"를 "비어 있다"로 해석하지 않는다** 원칙은 그대로 적용:
  events 로드 실패 시 **알림을 새로 만들지 않고 그 회차를 건너뛴다** (빈 배열로 착각해 전량 재발송 금지)
- **[project-kv-write-limit]** — 변화 없을 때 write 0회
- **[project-channel-open-policy]** — 채널별 오픈 기간이 달라 iCal 꼬리 블락이 생긴다.
  블락은 파서 필터에서 이미 제외되므로 오버부킹 오탐으로 잡히지 않는다 (구현 시 재확인 필요)
- **[project-trip-inquiry-hold]** — 트립은 **문의 단계에서도 iCal에 홀드를 내보내고, 거절 후 해제까지 30분+** 걸린다.
  → 문의가 들어왔다 빠지면 취소 알림이 뜰 수 있다. **정상 동작으로 본다**(방이 실제로 다시 열린 것). 다만 빈도 관찰 필요

## 미결정 사항 (사용자 확인 필요)

**Q1. 새 예약 알림 — 전부 없앨까, 트립만 없앨까?**
- (a) **전부 폐지** ← 요청하신 방향
- (b) 트립만 폐지, 에어비앤비·부킹·리브는 유지 (이 셋은 앞잘림이 없어 오탐이 안 남)

**Q2. 오버부킹 푸시를 새로 만들까?**
지금은 앱을 열어야만 빨간 셀로 보인다. 만들면 겹치는 순간 폰으로 온다.
- (a) **만든다** ← 권장. 가장 급한 일인데 지금은 알 방법이 없다
- (b) 화면 표시만 유지

**Q3. 취소 알림 범위**
- (a) **오늘 이후 날짜가 비게 될 때만** ← 권장 (오탐 없음)
- (b) 6개월 이내로 추가 제한 (기존 새 예약 알림과 같은 기준)

**Q4. 알림함에 쌓인 기존 미확인 "새 예약" 알림 (지금 3건)**
- (a) **배포 시 일괄 확인 처리** ← 권장. 어차피 오탐
- (b) 그대로 두고 직접 확인
