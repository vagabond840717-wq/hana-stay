# PLAN — 채널별 내보내기 주소 분리 (per-channel-ical)

작성일: 2026-08-06
발단: 603호 부킹닷컴 예약(9/8~9/12)이 부킹닷컴 자기 달력에서 사라진 사건

---

## 배경 — 무슨 일이 있었나

### 사건 경위

```
02:44  부킹닷컴 예약을 통합 iCal에 싣기 시작 (commit 490067e)
       → 그 전까지 부킹 예약은 단 한 번도 내보내진 적이 없었다
08:57  우리 KV에 603호 bk 9/8~9/12 정상 수집됨
09:33  부킹닷컴 피드에서 그 예약이 사라짐 (402호도 동시에)
       → 우리도 따라서 지움 → 에어비앤비·트립·리브에 그 날짜가 열림
~20:00 사용자가 부킹닷컴에서 연동 재설정 + 예약앱 블락 해제 → 복구
```

### 인과 사슬 (사용자 지적, 시각·동작 모두 부합)

```
부킹닷컴  "9/8~9/12 예약 있음"
   ↓ 우리가 수집
우리      통합 달력에 "Booking.com 예약 9/8~9/12" 로 실어 내보냄
   ↓ 부킹닷컴이 그 주소를 구독
부킹닷컴  "이 날짜는 남의 달력에서 온 블락이네"
          → 가져온 블락은 자기 iCal로 되내보내지 않는다
   ↓
우리      "예약이 사라졌다 = 취소됐나 보다" → 전 채널에 개방
```

**자기가 한 말이 한 바퀴 돌아 자기에게 돌아온 것.** 02:44 변경이 방아쇠였다.

### 근본 원인

`/ical/<호실명>` **주소가 하나뿐**이고, 그 하나에 **네 플랫폼 예약이 전부** 담긴다.
그래서 각 채널은 자기 예약까지 되돌려받는다.

## 설계

### 주소 구조

```
현행 (유지)   /ical/<호실명>            ← 네 플랫폼 전부 (레거시)
신규          /ical/<호실명>/ab         ← 에어비앤비용: bk + tr + lv + 수동블락
              /ical/<호실명>/bk         ← 부킹닷컴용:   ab + tr + lv + 수동블락
              /ical/<호실명>/tr         ← 트립닷컴용:   ab + bk + lv + 수동블락
              /ical/<호실명>/lv         ← 리브용:       ab + bk + tr + 수동블락
```

**레거시 주소는 동작을 한 글자도 바꾸지 않는다.** 마이그레이션이 끝날 때까지 기존 구독이 살아 있어야 한다.

### 필터 규칙

| 대상 | 자기 플랫폼 | 에어비앤비 블락(`Not available`) | 수동 블락 |
|---|---|---|---|
| 레거시 `/ical/<호실>` | 포함 (현행) | **제외** (현행 유지) | 포함 |
| `/ical/<호실>/ab` | 제외 | 제외 (자기 것이므로 자동) | 포함 |
| `/ical/<호실>/bk` | 제외 | **포함** ← 신규 | 포함 |
| `/ical/<호실>/tr` | 제외 | **포함** ← 신규 | 포함 |
| `/ical/<호실>/lv` | 제외 | **포함** ← 신규 | 포함 |

에어비앤비 블락을 다른 채널에 보내는 것이 **이번 변경의 두 번째 성과**다.
지금은 순환이 무서워 아무에게도 안 보내고 있어서, 에어비앤비에서 막은 날을 트립·부킹이 판다.

> 2026-08-06 오전 실제 사고: 402호 8/6을 레이트 체크아웃 때문에 에어비앤비에서 막았는데
> 트립에 전달되지 않아 8/6~8/8 예약 요청이 들어왔고 사용자가 거절해야 했다.

기존 규칙은 **그대로 유지**한다.
- `DTEND = cout` (알려진이슈 #21 — 절대 하루 빼지 않는다)
- `cout < 오늘`(KST) 인 항목 제외
- `HORIZON_ENABLED = false` 현행 유지

## 구현

### `ical-proxy/worker.js`

**① 라우팅** (현행 99~101행)

```js
if (path.startsWith('/ical/')) {
  const rest = decodeURIComponent(path.slice('/ical/'.length));
  const i = rest.lastIndexOf('/');
  let roomName = rest, target = null;
  if (i > 0) {
    const tail = rest.slice(i + 1);
    if (['ab','bk','tr','lv'].includes(tail)) { target = tail; roomName = rest.slice(0, i); }
  }
  return await exportIcal(env, roomName, target);
}
```

호실명에 `/`가 들어갈 일은 없지만, **마지막 조각이 알려진 채널 키일 때만** 채널로 해석하므로 안전하다.
`target === null` 이면 레거시 동작.

**② `exportIcal(env, roomName, target = null)`**

기존 루프의 필터 두 줄만 교체한다.

```js
for (const [key, bks] of Object.entries(roomBookings)) {
  // 채널별 주소: 그 채널 자기 예약은 돌려주지 않는다.
  // (돌려주면 채널이 "남의 블락"으로 인식해 자기 iCal에서 빼버린다 — 2026-08-06 부킹닷컴 사건)
  if (target && key === target) continue;

  for (const bk of bks) {
    // 레거시 주소에서만 에어비앤비 블락 제외 (순환 방지). 채널별 주소는 위에서 이미 걸러진다.
    if (!target && key === 'ab' && bk.summary?.toLowerCase().includes('not available')) continue;
    ...  // 이하 현행 그대로
  }
}
```

수동 블락 부분은 손대지 않는다 (모든 주소에 포함).

## 마이그레이션

배포해도 **아무것도 안 바뀐다** (레거시 주소 그대로). 채널에서 주소를 갈아끼워야 효과가 난다.

### 갈아끼울 개수 — 총 19개

| 채널 | 호실 |
|---|---|
| 에어비앤비 | 202, 203, 302, 401, 402, 501, 503, 601, 603 (9) |
| 부킹닷컴 | 302, 402, 501, 601, 603 (5) |
| 트립닷컴 | 402, 601, 603 (3) |
| 리브애니웨어 | 203, 401 (2) |

### 순서 — 부킹닷컴부터

지금 문제가 나고 있는 채널이므로 부킹 5개를 먼저 바꾸고 하루 지켜본다.
그다음 트립 → 리브 → 에어비앤비.

**에어비앤비는 마지막**에 바꾼다. 유일한 자동 예약 채널이라 가장 위험하고,
현재 정상 동작 중이므로 서두를 이유가 없다.

## 검증 계획

### 배포 직후 (마이그레이션 전)

레거시 주소가 **한 글자도 안 바뀌었는지** 확인한다. 이게 제일 중요하다.

```bash
# 배포 전 저장 → 배포 후 비교, 9개 호실 전부 diff 0 이어야 함
curl -s ".../ical/<호실>" > before_<호실>.ics
```

### 새 주소 확인

| 확인 | 기대 |
|---|---|
| `/ical/603 jnj/bk` | 부킹 예약(9/8~9/12) **없음**, 에어비앤비·트립 것 있음 |
| `/ical/603 jnj/ab` | 에어비앤비 것 없음, 부킹 9/8~9/12 있음 |
| `/ical/402 jnj/tr` | 트립 것 없음, **에어비앤비 블락 8/6 포함** ← 신규 |
| 네 주소 합집합 | 레거시 주소 + 에어비앤비 블락 |
| 존재하지 않는 채널 `/ical/603 jnj/xx` | 레거시와 동일 (호실명으로 해석되어 빈 달력) |

### 마이그레이션 후 (부킹 5개)

- 24시간 관찰: 부킹닷컴 피드에서 자기 예약이 다시 사라지는지
- 사라지지 않으면 **원인 규명 완료**, 나머지 채널 진행
- 사라지면 다른 원인 → 장부(ledger) 설계로 넘어감

## 위험 / 주의

- ⚠ **레거시 주소 동작이 바뀌면 전 채널이 즉시 영향받는다.** 배포 전후 바이트 비교 필수
- ⚠ 마이그레이션 중에는 한 채널이 옛 주소, 다른 채널이 새 주소를 보는 혼재 상태가 된다.
  두 주소 모두 "다른 채널 예약"은 담고 있으므로 **오버부킹 방향으로는 안전**하다
  (새 주소가 담는 정보가 레거시보다 적지 않다 — 에어비앤비 블락이 오히려 추가됨)
- ⚠ 에어비앤비 블락이 처음으로 트립·부킹에 나간다. **판매 가능일이 줄어드는 방향**이므로
  의도치 않게 막히는 날이 없는지 배포 후 각 채널 달력을 눈으로 확인
- 에어비앤비가 받은 블락을 되내보내지 않는다는 전제 위에 서 있다 (2026-08-06 실측).
  마이그레이션 후 에어비앤비 피드에 bk/tr 예약과 같은 날짜의 블락이 나타나는지 확인할 것
- 워커만 변경. 앱·KV 스키마 변경 없음. 되돌리려면 커밋 하나만 되돌리면 된다
