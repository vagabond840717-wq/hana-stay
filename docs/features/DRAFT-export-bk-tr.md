# 부킹·트립 예약 내보내기 정상화 (export-bk-tr) 스펙

## 요약
통합 iCal 내보내기(`/ical/<호실명>`)에서 **부킹닷컴 예약이 100% 누락**되고 **트립닷컴의 판매 미오픈 꼬리는 그대로 나가는** 문제를 고친다. 플랫폼별 필터를 분리하고, 숙박 기간 길이(30일 기준)로 "실제 예약"과 "판매 미오픈 기간"을 구분한다.

---

## 목적 및 배경

### 발견 경위
2026-08-06, 603호 부킹닷컴 예약(9/8~9/12)이 예약앱에는 보이는데 에어비앤비 달력이 그대로 열려 있는 것을 사용자가 발견.

### 원인 — [worker.js:450](../../ical-proxy/worker.js) 한 줄

```js
// exportIcal 내부
if (bk.summary?.toLowerCase().includes('not available')) continue;
```

에어비앤비가 준 블락을 되돌려주면 순환이 생기므로 만든 필터인데, **플랫폼 구분 없이 전부에 적용**된다.

부킹닷컴은 **실제 예약도 제목을 `CLOSED - Not available`로 보낸다** (손님 정보 비공개 정책). 따라서 이 필터에 부킹닷컴 예약이 전부 걸린다.

### 실측 근거 (2026-08-06 기준)

| 호실 | 부킹닷컴 원본 피드 | 내보내기(`/ical/`)에 포함? |
|------|---|---|
| 603 jnj | `20260908~20260912` (4박, 실제 예약) | ❌ 없음 |
| 601 jnj | `20270615~17`, `20270618~20`, `20270624~26` | ❌ 없음 |
| 402 jnj | `20261027~20261116` (20일) | ❌ 없음 |
| 302 jnj | (꼬리만) | ❌ 없음 |

→ **부킹닷컴이 연결된 302·402·501·601·603호 전부, 부킹 예약이 단 한 건도 다른 채널을 막은 적이 없다.** 오버부킹 상시 노출 상태.

### 반대 방향 문제 — 트립닷컴 꼬리가 나가고 있음

트립닷컴은 파서 단계에서 `not available`이 이미 제거되어(worker.js:428) 내보내기까지 통과한다. 그런데 트립닷컴은 **판매 미오픈 기간도 `RoomStatus Fully booked`로** 보낸다.

402호 내보내기 실측:
```
DTSTART:20270101  DTEND:20270615  SUMMARY:Trip.com 예약 (402 jnj)   ← 165일. 실제 예약 아님
```

→ 402호 에어비앤비·부킹닷컴이 **2027년 1~6월 통째로 닫혀 있을 가능성**. 매출 손실 방향의 버그.

### 채널별 "꼬리" 특성 (실측)

| 채널 | 미오픈 기간 표기 | 실측 사례 |
|---|---|---|
| 부킹닷컴 | `CLOSED - Not available` (예약과 동일) | 302/402/601/603 모두 **2028-02-05에서 끝남** |
| 트립닷컴 | `RoomStatus Fully booked` (예약과 동일) | 402: 2027-01-01~06-15 |
| 에어비앤비 | `Airbnb (Not available)` (예약은 `Reserved`) | 제목으로 구분 가능 |

**부킹·트립은 제목으로 구분이 불가능하다.** 남은 단서는 기간 길이뿐이다.

## 기능 상세

### 사용자 시나리오
1. 부킹닷컴으로 603호 9/8~9/12 예약이 들어온다
2. 다음 동기화(15분 주기) 때 워커가 이를 받아 통합 iCal에 포함시킨다
3. 에어비앤비·트립닷컴·리브애니웨어가 그 iCal을 읽어 9/8~9/11 판매를 닫는다 (9/12는 체크아웃일이라 판매 가능 — 기존 규칙 유지)
4. 부킹닷컴이 "2027년 10월 이후는 아직 안 엶"이라고 보낸 127일짜리 블락은 **내보내지 않는다**

### 동작 규칙

내보내기 대상 판정 (플랫폼별):

| 플랫폼 | 제목 필터 | 기간 필터 | 비고 |
|---|---|---|---|
| `ab` 에어비앤비 | `not available` 포함 → **제외** | 없음 | 현행 유지 (순환 방지) |
| `bk` 부킹닷컴 | **없음** (전부 통과) | **30일 이상 → 제외** | 변경 |
| `tr` 트립닷컴 | 없음 (파서에서 이미 처리) | **30일 이상 → 제외** | 변경 |
| `lv` 리브애니웨어 | 없음 (파서에서 이미 처리) | 없음 | **현행 유지** — 단기임대·수락제라 꼬리 없음 |

기간 = `체크아웃 - 체크인` (박 수). DTEND 계산 규칙은 **변경하지 않는다** (알려진이슈 #21).

### UI/UX
- 워커 단독 변경. **앱 화면 변경 없음.**
- 예약앱 달력 표시는 지금과 동일 (앱은 원본 피드를 직접 읽으므로 영향 없음)

## 기술 구현 방안

### 옵션 A — 기간 길이 기준 (권장)

```js
const NIGHTS = (a, b) => Math.round((new Date(b.y,b.m,b.d) - new Date(a.y,a.m,a.d)) / 86400000);
const MAX_EXPORT_NIGHTS = 30;

for (const bk of bks) {
  if (key === 'ab' && bk.summary?.toLowerCase().includes('not available')) continue;
  if ((key === 'bk' || key === 'tr') && nights(bk) >= MAX_EXPORT_NIGHTS) continue;
  // ... 기존 DTSTART/DTEND 생성 그대로
}
```

- 장점: 단순, 부수효과 없음, 숫자 하나만 바꾸면 조정 가능
- 단점: 30일 이상 장기 실제 예약을 못 막음 (부킹닷컴은 보통 30박 제한이라 드묾)

### 옵션 B — "피드 최대 종료일" 기준

꼬리는 항상 피드의 가장 마지막까지 이어진다(실측: 부킹 4개 호실 모두 2028-02-05 종료). 종료일이 피드 최대값과 같은 항목을 꼬리로 판정.

- 장점: 길이 무관, 장기 예약도 안전
- 단점: 꼬리가 2개 이상인 경우(603호: 30일짜리 + 127일짜리) 앞쪽 꼬리를 못 거름. 채널이 표기를 바꾸면 통째로 무너짐

### 옵션 C — 스냅샷 비교 (꼬리는 시간이 지나면 뒤로 밀림)

`tr_feed_prev`와 동일한 방식으로 직전 피드를 저장해두고, 시작일이 계속 밀리는 항목을 꼬리로 판정.

- 장점: 가장 정확
- 단점: 구현 복잡, KV 쓰기 증가, 판정까지 최소 2회 동기화 필요. 지금 오버부킹이 열려 있는 상황에 맞지 않음

### 권장: **옵션 A**
지금 뚫려 있는 구멍(부킹 예약 100% 누락)을 최소 변경으로 즉시 막는 것이 우선. 기준값은 상수 하나로 두어 나중에 조정 가능하게 한다. 옵션 B/C는 필요해지면 추가.

## 제약 및 주의사항

- ⚠ **전 채널 즉시 영향.** 에어비앤비·부킹닷컴·리브애니웨어가 모두 이 주소를 구독한다. 배포 즉시 반영됨
- ⚠ DTEND 계산은 **절대 건드리지 않는다** (알려진이슈 #21, 2026-08-01 오버부킹 재발 방지)
- ⚠ 배포 후 각 채널 달력을 **눈으로 확인**해야 한다. 에어비앤비는 가져온 블락을 자기 iCal로 되내보내지 않아 API로는 검증 불가
- 워커에 저장된 동기화 데이터가 실제 피드보다 약 한 달 뒤처져 있음 (603호 꼬리: 저장 `27/3/26~4/26` vs 실제 `27/4/26~5/26`). **별건으로 확인 필요**

## 결정 사항 (2026-08-06 사용자 승인)

1. ✅ **부킹닷컴 예약 내보내기 — 진행**
2. ✅ **판정 기준을 "기간 길이"에서 "판매 오픈 기간(굴러가는 기준선)"으로 변경** (2026-08-06 2차 결정)

   ### 채널별 판매 오픈 정책 (사용자 운영 방침)
   | 채널 | 오픈 기간 | 가짜 구분 |
   |---|---|---|
   | 부킹닷컴 · 트립닷컴 | **오늘부터 6개월** | 제목으로 구분 불가 → **날짜로 판정 필요** |
   | 에어비앤비 | 오늘부터 3개월 | 제목으로 구분 가능(`Not available`) → 현행 유지 |
   | 리브애니웨어 | — | 수락제 → 현행 유지 |

   - 부킹·트립의 판매 오픈 범위 **밖에 걸친 항목은 실제 예약일 수 없다** = 판매 미오픈 기간(가짜)
   - 규칙: **체크아웃이 `오늘 + 6개월 + 여유 7일`보다 뒤인 bk·tr 항목은 내보내지 않는다**
   - **체크아웃 기준**인 이유: 체크인 기준이면 402호 트립 가짜(`2027-01-01~06-15`)처럼 **경계 바로 안쪽에서 시작해 한참 뒤까지 이어지는 꼬리**를 놓친다. 진짜 예약은 판매 가능 범위 안에서 끝나고, 가짜 꼬리는 그 밖까지 뻗는다
   - **여유 7일**을 두는 이유: 채널이 "6개월"을 월말 단위로 끊는 등 미세하게 더 열어줄 수 있다. 실제 예약을 잘못 빼면 오버부킹이므로 안전한 쪽으로 여유를 준다. 가짜 꼬리는 수개월 단위로 뻗어 있어 이 여유로 새어나가지 않는다
   - 30박 길이 기준은 **폐기**. 603호 트립 `2027-03-24~26`(2박) 같은 **짧은 가짜**를 못 거른다
   - ✅ **하드코딩된 날짜가 없다** → 2027년 판매를 열어도 자동으로 따라간다 (상수 갱신 불필요)
3. ✅ **과거 예약 제외** — 체크아웃일이 오늘보다 이전인 건은 내보내기에서 뺀다
   - 근거: 이미 지난 날은 오버부킹이 발생할 수 없으므로 다른 채널에 알릴 이유가 없다
   - 판정 기준일은 **한국 시간(KST, UTC+9)** — 워커는 UTC로 도니 명시적으로 +9 보정
   - `cout < 오늘` 제외 / `cout === 오늘`은 유지 (오늘 체크아웃은 아직 유효)
4. ✅ 리브애니웨어 현행 유지 (단기임대·수락제)

### 확인 대기 (구현을 막지 않음)
- 402호 부킹 `2026-10-27~11-16` (20박) → 판매 오픈 구간 안이라 **내보내짐**. 실제 예약이 아니면 알려주시면 조정
- 601호 부킹 `2027-06-15~17` 외 2건 → 2027년이라 **제외됨** (사용자 확인: 27년 항목은 전부 가짜)
- ~~501호 부킹닷컴 피드 이벤트 0건~~ → **정상.** 501호는 아직 부킹닷컴 예약이 들어온 적이 없음 (사용자 확인, 2026-08-06). 연결 문제 아님
- 워커 저장 데이터가 실제 피드보다 약 한 달 뒤처짐 — 별건으로 확인
