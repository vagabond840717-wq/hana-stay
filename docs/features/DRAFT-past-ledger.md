# 과거 확정 원장 (past-ledger) 스펙

## 요약
지나간 날짜의 달력 재료를 매일 아침 한 번 굳혀 저장하고, 화면은 **오늘 이전 = 원장 / 오늘 이후 = iCal 피드**로 그린다.

---

## 목적 및 배경

### 발단 (2026-08-13 발견 / 2026-08-15 기준 갱신, 601호)
트립 예약 목록에는 `ZHANG/FENG 8/11 → 8/13` 이 있는데 예약앱은 **8/12 체크인**으로 표시했다.
**2026-08-15 현재 이 손님은 화면에서 완전히 사라졌다** (아래 "하루에 한 칸씩" 참고).

파일 대조로 확인한 원인:

| 확인 대상 | 값 |
|---|---|
| 트립 원본 iCal (08-15) | `DTSTART:20260813` / `DTEND:20260823` |
| 아카이브에 남은 같은 숙박 | `2026-08-10 → 2026-08-23` |
| 저장된 경계 (`tr_cuts`) | 601 jnj `8/11`, `8/13`, `8/17` |
| 트립 실제 예약 | 8/8→8/11, 8/11→8/13, 8/13→8/17, 8/17→8/23 (4팀) |

1. 트립은 **연속 예약을 한 덩어리로 뭉쳐** 보낸다 → 사용자가 `tr_cuts`로 경계를 손수 긋는다
2. 트립은 **투숙 중인 숙박도 앞에서 잘라낸다.** 같은 숙박이 아카이브엔 `8/10 시작`, 08-13엔 `8/12 시작`, 08-15엔 `8/13 시작` (끝날짜 `8/23`은 계속 동일)
3. 잘리면서 **`8/11` 경계가 통짜 바깥으로 밀려나** 아무 일도 안 하는 상태가 됐다 (`applyCuts`는 `cin < 경계 < cout` 일 때만 자른다)
4. 아카이브에 `8/10 → 8/23` 이 남아 있으나 **`mergeArchiveIntoRooms`가 `cout < 오늘` 인 것만 복원**한다 ([app/JnJ booking/index.html](../../app/JnJ%20booking/index.html) `mergeArchiveIntoRooms`) → 아직 투숙 중인 이 숙박은 복원 대상에서 제외
5. 결과: `8/11 = 아웃만`(아카이브 `8/8→8/11`에서 복원), `8/12 = 인`(현재 피드) → **8/11 밤이 빈칸**

**앱·워커의 날짜 계산 오류가 아니다.** 외부 피드가 변하는데 앱이 자기 기록을 안 꺼내 쓴 것이 원인이다.

### 잘리는 규칙 — `DTSTART = UTC 기준 어제` (실측 3회)

| 수신 DTSTAMP (UTC) | 한국시간 | 파일의 `DTSTART` | UTC오늘−1 |
|---|---|---|---|
| `20260813T002620Z` | 08-13 09:26 | `20260812` | 8/12 ✔ |
| `20260813T004121Z` | 08-13 09:41 | `20260812` | 8/12 ✔ |
| `20260814T151414Z` | **08-15 00:14** | `20260813` | 8/13 ✔ |

**한국시간이 아니라 UTC 기준으로 자른다.** 따라서 한국시간 09:00 을 넘기면 그날 UTC가 넘어가면서
**어제 날짜가 피드의 맨 앞이 된다.** 날짜 `X` 가 피드에 남아 있는 시한은 **KST `X+2` 일 09:00** 이다.
→ 굳히기를 `X+1` 일 낮에 하면 약 25시간의 여유가 있다.

### 트립만 문제인 이유 — 에어비앤비와 나란히 대조 (2026-08-15 실측)

| | 상황 | 피드가 주는 시작일 |
|---|---|---|
| **에어비앤비 302호** | 8/3 입실 → 8/15 퇴실 (투숙 중) | `2026-08-03` — **12일 전 그대로** |
| **트립 601호** | 투숙 중 (8/23 퇴실) | `2026-08-13` — **계속 밀림** |

- **끝난 예약이 피드에서 사라지는 것은 모든 플랫폼 공통**이고, 이는 `mergeArchiveIntoRooms`(`cout < 오늘`)가 이미 완전히 보완한다
- 문제는 **투숙 중인 숙박의 모양이 변하는 것**이고, 이는 트립에서만 관측된다
- 트립만 **① 뭉쳐 보냄 + ② 투숙 중에도 앞을 자름** 두 가지를 동시에 한다. 하나만이면 피해가 없다
  - 뭉치기만 하고 안 자르면 → 경계가 늘 통짜 안쪽 → 무해
  - 자르기만 하고 안 뭉치면 → 경계를 그을 일이 없음 → 무해
- 부킹닷컴·리브애니웨어는 뭉쳐 온 사례가 아직 없다 (#14)

### 하루에 한 칸씩 지워진다 (피해 진행형)

`ZHANG/FENG 8/11 → 8/13` (2박) 이 화면에서 사라진 경과:

```
08-13 시점:  8/11 사라짐              (1칸)  → 8/11 아웃, 8/12 빈칸, 8/13 인
08-15 시점:  8/11 · 8/12 둘 다 사라짐  (2칸)  → 이 손님 기록이 화면에서 완전 소멸
```

**시간이 지날수록 손실이 커진다.** 굳히기를 도입하지 않으면 트립 투숙 기록은 계속 이런 식으로 잘려 나간다.

### 왜 원장인가
과거를 **"예약 덩어리"로** 보관하면 그 덩어리 모양이 외부 사정으로 계속 변한다. 변하는 것을 보관하면 화면도 계속 흔들린다.
**날짜 칸 단위로 굳히면** 트립이 뭘 뭉치든 잘라내든 지난 표시가 바뀌지 않는다.

### 부수 효과
- 취소된 예약이 기록에 영구 잔류하는 문제(#16 근본 원인)가 **신규분에 한해** 해소된다 — 굳히는 시점에 이미 빠져 있으므로
- 사용자가 그은 경계의 **결과**가 굳으므로, 경계가 나중에 무효화돼도 지난 화면은 유지된다

### ⭐ 청소 횟수 통계가 지금 축소 집계되고 있다 (2026-08-15 확인)

`calcCleanings()` 는 **`archiveData` 의 예약 건수**를 센다 (그 달에 `cout` 이 있는 건). 즉 **경계(`tr_cuts`) 적용 전 통짜**를 센다.
→ 트립에서 손님이 4팀 바뀌어도 **통짜 하나 = 청소 1회**로 계산된다.

601호 2026년 8월 실측 대조:

| 퇴실일 | 앱이 세는가 | 실제 |
|---|---|---|
| 8/3 (ZHANG/JIAYU, 3박) | ✔ short | ✔ short |
| 8/11 (YANG/LIU, 3박) | ✔ short | ✔ short |
| 8/13 (ZHANG/FENG, 2박) | ✗ **누락** | ✔ short |
| 8/17 (ZHOU/TINGTING, 4박) | ✗ **누락** | ✔ long |
| 8/23 (KAN/TSZ, 6박) | ✔ (통짜 `8/10→8/23` 1건, 13박 → long) | ✔ long |
| 7/30→8/3 (Chai/Yurou, **취소건**) | ✗ **허위 계상** long | — |
| **합계** | **4회** (short 2 · long 2) = **140,000원** | **5회** (short 3 · long 2) = **165,000원** |

- **누락 2건 + 허위 1건.** 사용자가 손수 그은 경계가 통계에 전혀 반영되지 않는다
- 원장은 **경계 적용 후 조각**을 담으므로, 원장 기준으로 세면 정확해진다
- 가동률(`calcOccupancy`)은 **밤 수**를 세므로 통짜든 조각이든 동일 → **영향 없음.** 청소 횟수만 해당된다

## 기능 상세

### 사용자 시나리오
사장님은 아무것도 새로 하지 않는다. 지금처럼 트립 통짜를 손으로 나누기만 하면 된다.
차이는 **며칠이 지나도 그 결과가 화면에서 사라지지 않는다**는 것뿐이다.

### UI/UX
**화면 변화 없음.** 새 버튼·새 화면·새 표식 없다. 지난 날짜가 정확해질 뿐이다.

### 동작 규칙

**① 굳히는 대상** — 어제 이전 날짜 중 아직 안 굳은 날

**② 굳히는 시각 — 안전창 `KST 07:30 ~ 17:30`**

known-issues #28에서 확인된 트립의 자동 규칙 `전략 제어 – 당일 객실 마감` 때문이다:

```
매일 17:59:59  그날을 만실로 바꿈   → 피드에서 퇴실일이 하루 밀려 나옴
다음날 07:00   객실 있음으로 되돌림 → 정상 복귀
```

**저녁 6시 ~ 다음날 아침 7시 사이의 피드는 왜곡돼 있다.** 이 시간대에 굳히면 **틀린 상태가 영구 고착된다.**
→ 반드시 `07:30 ~ 17:30` 사이에만 굳힌다.

**시한과 겹쳐 보면 안전창이 유효하다:**

```
날짜 X 가 피드에 남아 있는 시한  =  KST (X+2)일 09:00   (DTSTART = UTC 어제 규칙)
굳히는 시점                      =  KST (X+1)일 07:30~17:30
                                    → 최소 약 15시간, 최대 약 25시간 여유 ✔
```

실측 확인 — `KST 08-13 09:26` 수신분에 어제(`20260812`)가 남아 있었다.

**③ 재료만 저장하고 판정은 앱이 한다**
원장에는 **그날 유효했던 예약 조각의 `cin`/`cout`** 만 담는다. 셀 색·라벨 판정(`cellTypeFor` 등)은 **저장하지 않는다.**
→ 판정 로직이 세 번째로 복제되는 것을 막는다 (known-issues #2 위험 회피)

**④ 과거는 다시 자르지 않는다**
원장에 담긴 조각은 이미 경계가 적용된 결과다. 렌더 시 `applyCuts`를 **과거 구간에 다시 걸지 않는다.**

**⑤ 한 번 굳은 날은 안 바꾼다**
자동 갱신·자동 삭제 없음. (#27 교훈: 사용자가 손으로 만든 데이터를 자동으로 지우는 규칙은 위험하다)

## 기술 구현 방안

### 저장 구조

**KV 키: `ledger_YYYY-MM`** (월별 분리)

월별로 나누는 이유 — 매일 쓰는 값이 작아지고(KV write 한도 원칙), 통계는 필요한 달만 읽으면 된다.

```js
// ledger_2026-08
{
  "601 jnj": {
    "20260811": { "tr": { "cin": "20260811", "cout": "20260813" } },
    "20260812": { "tr": { "cin": "20260811", "cout": "20260813" } },
    "20260808": { "tr": { "cin": "20260808", "cout": "20260811" } }
  }
}
```

- 날짜 칸 하나가 **어느 예약 조각에 속했는지**를 기록한다
- `cin` 을 담으므로 **비밀번호/메모 키(`bkKey`) 복원이 가능하다** (조각별 분리 유지 — #13)
- 렌더 시 연속된 같은 `(플랫폼, cin, cout)` 을 묶으면 조각 목록이 그대로 복원된다
- 수동 블락은 `manual_blocks` 가 이미 영구 보관이므로 **원장에 넣지 않는다**

용량: 9호실 × 약 30일 × 대부분 1플랫폼 → 월 파일 수십 KB 수준.

### 굳히는 시점 — 옵션 비교

**옵션 A: 전용 cron `0 0 * * *` (= KST 09:00) 추가**
- 장점: 하루 1회로 명확
- 단점: 그 한 번이 실패하면 **그날 치를 잃는다.** 트립은 다음날이면 그 날짜를 이미 잘라내 복구 불가

**옵션 B (권장): 기존 5분 cron 안에서 안전창 검사**
- `KST 07:30~17:30` 이고 + 아직 안 굳은 어제 이전 날짜가 있으면 굳힌다
- 한 번 실패해도 5분 뒤 다음 tick이 이어받는다 (**멱등**)
- 이미 굳은 날은 건너뛰므로 **KV write는 하루 1회**로 유지된다
- 웹 검색 결과에서도 cron 핸들러의 멱등성이 권장 사항으로 확인됨

**권장: 옵션 B**

### 재료 조립

워커가 굳힐 때 쓰는 재료:

```
synced_bookings (현재 피드)
  + extra_tr_cuts (경계 적용)
  + booking_archive (피드에서 이미 사라진 과거분 보완)
```

`applyCuts` 를 워커에 이식해야 한다 (현재 예약앱·청소앱 2곳에 존재 → 3곳). 순수 날짜 계산 20줄 남짓이라 이식 위험은 낮으나, **known-issues #2 대상이므로 문서에 명시**한다.

대안(앱이 굳히기)은 **채택하지 않는다** — 앱을 며칠 안 열면 그 사이 트립이 재료를 잘라내 복구 불가.

### 소급 채우기 (최초 1회)

기존 `booking_archive` 13개월치로 과거 원장을 생성한다.

- **601호 `8/11`·`8/12` 문제가 이때 자동 복구될 가능성이 높다.** 아카이브의 `8/10 → 8/23` 에 경계 `8/11`·`8/13`·`8/17` 을 적용하면 `8/11 = 아웃/인`, `8/12 = 숙박중`, `8/13 = 아웃/인` 으로 복원된다
- **소급 채우기는 하루라도 빨리 하는 게 좋다.** 아카이브의 `8/10 → 8/23` 이 유일한 복구 재료인데, 이것도 트립이 더 잘라 보내면 언젠가 갱신될 수 있다
- **한계**: 아카이브에는 취소분이 섞여 있다 (601호 `7/30→8/3` 취소건 실재). 이 부분은 부정확하게 채워진다 — 사용자 결정으로 **별도 표식·수정 UI는 만들지 않는다**

### 앱 렌더 변경

```
날짜 < 오늘  →  원장에서 복원한 조각으로 판정
날짜 >= 오늘 →  지금 그대로 (피드 + applyCuts)
```

- 셀 단위로 어느 목록을 쓸지 고르므로 **두 구간이 겹치지 않는다.** 오늘을 걸친 예약도 자연스럽게 이어진다
- `mergeArchiveIntoRooms` 의 과거 담당 역할을 원장이 가져간다. 아카이브는 **통계 백업·소급 채우기 재료**로 유지
- `isOverbooking` 의 "오늘 이전 판정 제외"(#16)는 **그대로 둔다** — 소급 채우기분에 취소가 섞여 있으므로
