# 트립닷컴 수동 예약 기입 (manual-trip-booking) 스펙

## 요약
트립닷컴 9개 호실을 **전부 수동**으로 운영한다. 날짜 칸을 눌러 **`🔒 블락`이냐 `🌐 트립 예약`이냐를
직접 골라** 적으면, 지금 있는 배관을 그대로 타고 에어비앤비·부킹·리브가 그 날짜를 막는다.
수락 전에는 앱이 **"그 구간에 완전히 빈 호실"**을 뽑아 줘서 잘못 수락하는 일을 막는다.

---

## 확정된 방향 (2026-09-17 사용자 결정)

| 항목 | 결정 |
|---|---|
| 트립 동기화 | **포기.** 9개 전부 수동 기입 |
| 구분 방식 | 날짜 칸 누르면 **`🔒 블락` / `🌐 트립` 중 직접 선택** (아이콘으로 갈라 표시) |
| 반대 방향 방어 | **수락 전에 사람이 앱을 보고 판단** → 앱이 그 판단을 도와준다 |
| 기존 연동 3개 호실 | 수동으로 통일 → `trUrl` 전부 제거 |

**전부 수동으로 통일한 덕에 위험 하나가 사라졌다.**
자동·수동을 섞으면 손으로 적은 게 트립 전용 주소(`/ical/<호실>/tr`)로 되돌아가 예약이 두 번
겹쳐 보인다. 9개 다 수동이면 트립이 애초에 우리 달력을 구독하지 않으므로 그 구멍이 없다.

## 목적 및 배경

### 상황
- 트립닷컴은 **호실 1개당 사업자등록증 1개**를 요구 → 지금은 3개만 올려 둠
- 노출을 늘리려 **사업자 1개 밑에 3개씩 × 3 = 9개**로 올린다
- **수락제**로 받고, **iCal 동기화는 끊긴다**

### 왜 동기화가 끊기나
달력에는 도장이 하나뿐이다 — "찼음". 방이 3개면 *"3개 중 1개만 팔렸음"* 을 찍을 도장이 없다.
그래서 재고 2개 이상인 방 타입은 어느 OTA에서도 iCal 연동이 안 된다
(부킹닷컴은 문서에 *"방 타입당 최대 1유닛"* 이라고 못 박아 뒀다).

### 이미 깔려 있는 배관 — 새로 만들 게 거의 없다
```
예약앱 날짜 칸 → 저장 (saveBlocksMerged)
   → KV extra_manual_blocks
   → exportIcal 이 별도 VEVENT 로 내보냄 (worker.js 783~795행)
   → /ical/<호실> · /ab · /bk · /lv  ← 전 주소에 다 나감
   → 에어비앤비·부킹·리브가 그 날짜를 막는다  ✔
   → 청소앱도 같은 KV 를 읽어 표시              ✔
```
#22 기록을 보면 사용자는 이미 *"202호에 33m2 등 iCal 미연동 플랫폼 예약 표시용"* 으로 이 길을 썼다.

### 부족한 것 4가지
| # | 부족한 것 | 지금 |
|---|---|---|
| 1 | **구분** | 블락은 전부 똑같은 회색. 청소로 막은 날인지 트립 손님이 든 날인지 색이 같다 |
| 2 | **입력 속도** | 칸 누르고 → 시작일 → 종료일 → 사유 → 저장. 수락제라 예약마다 반복, 호실 3배 |
| 3 | **수락 판단** | 없다. 2~3박이면 달력 칸을 눈으로 여러 개 훑어야 한다 → **여기서 실수가 난다** |
| 4 | **집계** | 통계는 `archiveData`(워커 아카이브)만 읽는다. 손으로 적은 건 **한 건도 안 잡힘** |

추가 안전 문제 — **`isOverbooking`은 수동 블락을 세지 않는다** (index.html 1208행, 4개 피드만 셈).
손으로 적은 트립 예약이 에어비앤비 예약과 겹쳐도 ⚠️ 경고가 안 뜬다.

## 기능 상세

### 시나리오 A — 예약 요청이 왔다 (수락 판단)
1. 트립에 **9/10~9/12(2박)** 요청이 뜬다
2. 예약앱 상단 **`🌐 수락 확인`** → `[체크인 9/10] [2박]`
3. 앱이 **그 구간이 처음부터 끝까지 완전히 빈 호실**만 뽑아 준다
   ```
   ✅ 받을 수 있음   703호 · 601호
   ❌ 안 됨          302호(9/11 에어비앤비)  402호(9/10 부킹)  …
   ```
4. `703호` 탭 → 그 자리에서 **트립 예약으로 기입**까지 끝 → 트립에서 수락 누르고 703호 배정

> 이게 3번 부족함을 메운다. 눈으로 훑는 대신 앱이 구간 전체를 한 번에 확인한다.

### 시나리오 B — 날짜 칸에서 바로 적기
1. **703호 9/10 칸을 탭**
2. 상세 아래에서 **어느 쪽인지 고른다**
   ```
   🌐 트립 예약        🔒 블락
   ```
3. `🌐 트립 예약` → 체크인 9/10 은 이미 채워져 있음 → **`[1박] [2박] [3박] [직접]`** 중 탭
4. 저장 → 달력에 **트립 색 + 🌐** 로 체크인·체크아웃이 그려진다

### 동작 규칙
- 입력은 **체크인·체크아웃**으로 받는다 (다른 예약과 같은 말)
  - 저장은 기존 블락 모양 그대로 → `end = 체크아웃 − 1일` 로 변환
  - 예: 9/10 인 · 9/12 아웃(2박) → `start=9/10, end=9/11` → 내보낼 때 `DTEND=9/12` ✔
  - 화면에 되돌려 보여줄 때는 `체크아웃 = end + 1일`
- **박수 버튼**으로 날짜 고르는 수고를 없앤다
- 메모란은 **선택 입력** (게스트 이름·예약번호). 비워도 저장된다
- `🔒 블락`은 **지금 그대로** (시작·종료·사유). 아무것도 안 바뀐다

### 달력 표시
- `platform` 붙은 것 → **그 플랫폼 색 + 🌐**, 체크인/체크아웃 마커도 일반 예약처럼 (`인`/`아웃`)
- `platform` 없는 기존 블락 → **지금 그대로 회색 🔒** (기존 화면 1칸도 안 바뀐다)

## 기술 구현 방안

### 권장: 기존 블락에 `platform` 한 칸만 더하기
```js
// 기존:  {roomName, startY,startM,startD, endY,endM,endD, reason}
// 추가:  {... , platform:'tr'}      ← 없으면 지금까지의 그 회색 블락
```
- **워커 `worker.js` 0줄 수정.** `exportIcal` 은 블락 배열을 그냥 순회할 뿐이라
  칸이 하나 늘어도 모르고 지나간다 → **전 채널 차단은 지금 그대로 작동** ✔
- 저장은 `saveBlocksMerged` 그대로 → #22·#26·#27 이 막아 둔 병합 안전장치를 **그대로 물려받는다**
- 청소앱도 같은 KV 를 읽으므로 **저절로 반영**
- 마이그레이션 **불필요**, 되돌리기도 `platform` 무시하면 즉시 원상복구

### 기각: `manual_bookings` 새 저장소 신설
예약과 똑같은 `{cinY..coutD}` 모양으로 저장하면 개념은 깔끔하지만 —
`exportIcal` 을 고쳐야 하고(전 채널이 동시에 바뀌는 자리), 청소앱도 새 키를 읽어야 하고,
저장 병합을 처음부터 다시 짜야 한다(#22 류 재발 위험). **얻는 건 모양뿐, 위험 대비 소득이 없다.**

## 데이터 변경

```js
// KV: extra_manual_blocks  (키·구조 그대로, 칸 하나만 추가)
{
  roomName: "703호",
  startY:2026, startM:8, startD:10,   // m = 0-indexed
  endY:2026,   endM:8,   endD:11,     // ⚠ end 는 '포함'. 체크아웃 = end + 1일
  reason: "김OO / 예약번호 123",
  platform: "tr"                      // 'tr'|'bk'|'lv'|'ab'. 없으면 = 기존 회색 블락
}
```
**마이그레이션 불필요.** 기존 블락은 `platform` 이 없으니 지금까지와 똑같이 회색으로 뜬다.

## 제약 및 주의사항

### ⚠ 트립 쪽은 여전히 스스로 막지 않는다
```
트립에서 예약 → 앱에 적기 → 에어비앤비·부킹·리브 막힘   ✔ 자동
에어비앤비에서 예약 →            트립은?                ✗ 안 막힘
```
트립이 판 날짜는 트립이 자기 재고에서 뺀다. 문제는 **다른 채널이 판 날짜를 트립이 모른다**는 것.
그래서 **수락 전 앱 확인이 유일한 방어선**이다 → 시나리오 A 가 이 스펙의 핵심.
겹치는 요청은 거절해야 하고, **거절이 잦으면 노출·순위 불이익**이 있을 수 있다
(트립 호스트 페널티 기준은 공개 문서를 못 찾았다 — 추측하지 말고 **트립 담당자에게 확인**).

### ⚠ 호실명을 바꾸지 말 것
`bkKey`·`manual_blocks` 모두 **호실명을 키로 쓴다** → 바꾸면 데이터가 고아가 된다.
트립 등록 때 이름을 새로 짓더라도 **앱 안의 호실명은 건드리지 않는다.**

### 기존 체크리스트
- 날짜는 `getFullYear/getMonth/getDate` 로컬 방식만. `toISOString()`·`new Date('YYYY-MM-DD')` 금지 (#30)
- 월 값은 0-indexed
- 저장은 반드시 `saveBlocksMerged` 경유. 서버를 못 읽으면 쓰지 않는다 (#22·#26·#27)
- `render()` → `attachCellClicks()` 체인 유지
- 트립 당일잠금(#28)·앞잘림 복원(#29)은 **피드 교정 로직**이라 손으로 적은 블락엔 닿지 않는다 → 무관
- 트립 피드가 사라지므로 `tr_cuts`(예약 경계)·`tr_feed_prev`(⚠확인)는 **할 일이 없어진다**.
  기능은 그대로 두되(옛 데이터 표시용), 새로 생길 일은 없다

## 트립 등록 구조 (확정)

```
사업자 1  →  숙소 1  →  객실 3개
사업자 2  →  숙소 2  →  객실 3개     =  트립 리스팅 9개
사업자 3  →  숙소 3  →  객실 3개
```

**트립 리스팅 9개 ↔ 실제 호실 9개가 1:1 대응한다.**
→ 요청이 오면 **어느 객실인지 특정된다** → 어느 물리 호실인지 바로 안다
→ 시나리오 A 는 **그 호실 하나의 구간만 검사**하면 끝. 묶음(그룹) 개념이 필요 없다

**권장** — 트립 객실 이름을 **실제 호실명 그대로**(`302호`·`402호`…) 붙여 둔다.
요청 화면에 뜬 이름으로 앱에서 바로 찾을 수 있어 옮겨 적을 때 실수가 없다.
(앱 안의 호실명은 **절대 바꾸지 않는다** — `bkKey`·`manual_blocks` 가 호실명을 키로 쓴다)

> 참고: 객실이 각각 재고 1 인 구조라면 이론상 객실별 iCal 1:1 연동이 가능한 모양이다.
> 다만 트립이 **숙소 하위 객실에도 iCal 메뉴를 열어 주는지**는 확인되지 않았고,
> 사용자는 **수동 운영으로 결정**했다. 나중에 익스트라넷에 그 메뉴가 보이면 재검토할 여지는 있다.

## 미결정 사항 (사용자 확인 필요)

1. **손으로 적은 트립 예약을 통계(점유율)에 넣을 것인가?** — 기본 방향: **넣는다**
   - 안 넣으면 9개 호실 트립 매출이 통계에서 통째로 빠져 실제보다 낮게 나온다
   - 기존 통계는 블락을 실제 예약이 아니라고 보고 제외해 왔다 (`booking-archive-stats.md`)
     → `platform` 이 붙은 것만 세고, 회색 블락은 지금처럼 계속 제외한다
   - **구현 순서상 마지막 단계**라 지금 확정하지 않아도 앞 단계 진행에 지장 없다
